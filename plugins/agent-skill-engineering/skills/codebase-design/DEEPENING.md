# 深化模块

仅在已经识别出具体浅模块，并需要决定依赖接缝、迁移方式或测试策略时读取本文。词汇以 [SKILL.md](./SKILL.md) 为准。

## 依赖分类

先按依赖性质分类，再决定接缝和测试方式：

1. **进程内依赖**：纯计算或内存状态。通常直接收进深化后的模块，通过新接口测试，不额外建立 adapter。
2. **本地可替代依赖**：数据库、文件系统等具有可信本地替代物的依赖。优先在模块内部使用替代物完成测试，不为了暴露测试细节扩大外部接口。
3. **自有远程依赖**：跨网络调用的自有服务。仅当传输方式或测试替代确实形成多个行为变体时，在接缝处定义 port，由 HTTP、RPC、消息队列或内存 adapter 满足。
4. **真实外部依赖**：无法控制的第三方服务。将外部交互约束在清晰接缝后，生产 adapter 调用第三方，测试 adapter 提供可控行为。

## 接缝纪律

- 区分内部接缝与外部接口。内部测试需要替换依赖，不代表调用者也必须看见该接缝。
- 能指出至少两个有意义的 adapter 或行为变体时，接缝才有证据；单一实现外再包一层通常只是间接层。
- 不得为假想的未来、框架形式或方便 mock 引入接缝。
- 接缝的位置必须让业务规则、调用顺序和错误处理仍集中在深化后的模块内，而不是泄漏到 adapter 或调用者。

## 安全迁移与测试

1. 先记录现有调用者、可观察行为、错误模式和关键测试覆盖。
2. 定义深化后的接口，并证明调用者需要知道的事实减少、核心行为没有丢失。
3. 通过新接口补齐行为测试，再迁移调用者；宽范围机械迁移交由 `to-task` 按 expand-contract 拆解。
4. 只有确认新测试覆盖同等行为、旧测试只绑定已被替代的内部结构且没有独立回归价值时，才删除旧测试。
5. 用原有验收路径验证迁移前后行为一致，并遵守当前任务的提交与副作用边界。
