# 设计两次

当用户希望为已选定的深化候选探索不同接口时，使用以下并行子 Agent 模式。本方法来自 Ousterhout 的“设计两次”：第一个想法通常不是最好的。

本文使用 [SKILL.md](./SKILL.md) 中的**模块**、**接口**、**接缝**、**适配器**和**杠杆**词汇。

## 流程

### 1. 界定问题空间

创建子 Agent 前，先向用户说明所选候选的问题空间：

- 新接口需要满足的约束；
- 它依赖什么，以及这些依赖属于 [DEEPENING.md](./DEEPENING.md) 中的哪一类；
- 一份用于具体说明约束的粗略代码草图。它只是示意，不是方案。

向用户展示后立即进入第 2 步。用户阅读和思考的同时，子 Agent 并行工作。

### 2. 创建子 Agent

并行创建至少三个子 Agent，每个 Agent 必须为深化后的模块设计一个**显著不同**的接口。

为每个 Agent 提供独立的技术简报，包括文件路径、耦合细节、[DEEPENING.md](./DEEPENING.md) 中的依赖类别，以及接缝背后包含什么。该简报独立于第 1 步面向用户的问题空间说明。为每个 Agent 分配不同约束：

- Agent 1：最小化接口，目标是不超过 1–3 个入口，尽量提高每个入口的杠杆。
- Agent 2：覆盖已确认的灵活性和扩展需求，不为未知未来增加表面积。
- Agent 3：优化最常见调用者，让默认用法最简单。
- Agent 4（适用时）：围绕跨接缝依赖设计 ports-and-adapters 方案。

简报同时包含 [SKILL.md](./SKILL.md) 词汇和 CONTEXT 词汇，使各 Agent 使用一致的架构语言与项目领域语言。

每个 Agent 输出：

1. 接口：类型、方法、参数，以及不变量、顺序和错误模式；
2. 调用者如何使用接口的示例；
3. 接口背后隐藏的实现复杂度；
4. 依赖策略和适配器，参见 [DEEPENING.md](./DEEPENING.md)；
5. 取舍：哪里杠杆较高，哪里较薄。

### 3. 展示并比较

依次展示各方案，让用户逐个理解，再用文字比较。对比它们的**深度**（接口杠杆）、**局部性**（变更集中在哪里）和**接缝位置**。

比较后明确推荐你认为最强的设计并解释原因。如果不同设计的部分能够良好组合，可以提出混合方案。给出明确判断，而不是只提供选项菜单。
