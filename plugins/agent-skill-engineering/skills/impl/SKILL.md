# Impl

`-w` 只强制使用隔离 worktree，`-a` 只强制使用子 Agent 或 workflow 编排。两者独立且可组合，均不改变实现范围、任务依赖、提交和安全规则。

## 1. 确定实现单元

开始前检查主工作区已有的已暂存、未暂存和未跟踪改动。已有改动与本次范围重叠且无法可靠分离时暂停。

使用当前任务已经由 `project-knowledge load` 返回的 CONTEXT 术语与 RULE，不自行定位或再读领域文档。项目未采用知识结构或 Hook 已提醒知识不可用时，继续执行并如实说明。

从输入中确定独立实现单元：

- **任务卡输入**：读取目标、现状、方案和验收条件。一张任务卡形成一个实现单元；发现卡内包含多个可独立验收和回滚的目的时停止并返回拆卡。
- **对话输入**：提取目标、范围、已确定方案和验收方式；上下文足够时直接实现，不要求先生成任务卡。多个独立目标分别形成实现单元。

当前实现涉及模块职责、接口表面积、依赖接缝、adapter、测试面或模块深浅时，读取 `codebase-design`：

- **任务卡输入**：只用其词汇和准则把已确定的模块形状映射到真实代码，不得重新选择或扩大方案；代码事实证明方案不可行时按下方停止条件处理。
- **对话输入**：当前范围已经授权实现且模块形状可由需求、代码和项目规则收口时，用它完成必要设计；存在影响显著的可行方案分歧时，先调用 `grill-with-docs`，用户确认前不得实现。

任务卡存在 `Blocked by` 时，读取引用的任务卡；只有依赖全部完成才解锁。一次输入多个任务时，只实施当前已解锁的任务。一次输入多张任务卡时，每张已解锁任务卡必须在彼此隔离的执行上下文中实施；可以使用独立 Agent、fork Agent、workflow、独立任务或宿主提供的等效机制。存在依赖时，前置任务提交并集成后，后续任务基于最新目标分支实施。

上下文隔离不决定 worktree、执行者或串并行策略。并行任务必须使用独立 worktree，否则串行实施。

只有缺失信息真正阻塞实现时，才调用 `grill-with-docs` 与用户对齐。

## 2. 选择执行方式

用户明确指定 worktree 或当前工作区时直接遵循。未指定时自动选择：

- **当前工作区**：范围集中，已有改动不重叠，或 worktree 的创建与集成开销大于隔离收益
- **隔离 worktree**：需要保护已有改动，范围较广或风险较高，或多个实现单元需要隔离

开始实现前简要说明选定方式和一项关键依据，不请求确认。仅当改动归属、实现范围或隔离收益无法从任务卡和代码事实中判断，且两种方式利弊接近时，才使用提问工具。确定后除非用户重新指示，不自动切换或降级。

`-a` 不强制使用 worktree，仍按本节规则选择当前工作区或隔离 worktree。

确定为隔离 worktree、或使用了 `-w` / `-a` 时，完整读取 [ISOLATION.md](./ISOLATION.md) 再开始实现。

## 3. 实现、验证与提交

逐个实现单元执行：

1. 查看现有代码和相关 Skill，将已确定方案映射到实际结构，只做范围内的最小修改；优先复用现有能力，不确定的框架 API 先查本地用法再查 references。
2. 不重新选择已收口的主要方案。代码事实证明方案不可行或矛盾时停止并报告；发现需要扩展范围、改变方案或增加任务依赖时重新拆分。
3. 完成与范围相称的测试和验收，如实保留验证边界。
4. 全部通过后调用 `atomic-commit`，以当前实现单元为提交边界检查 staged diff 并完成一个本地提交；发现范围外的独立目的时停止并报告。任务卡与实现位于同一仓库时，提交前将对应任务改为 `completed`。

默认不调用 `code-review`。用户明确要求代码评审时，将它作为独立流程调用，不把它作为本 Skill 的默认完成门槛。

当前工作区模式按依赖顺序串行完成上述循环。

任务卡与实现位于不同仓库时，实现提交后在任务仓库将对应任务改为 `completed`。同一 `tasks/` 目录下全部任务均为 `completed` 时，统一改为 `archived`。
