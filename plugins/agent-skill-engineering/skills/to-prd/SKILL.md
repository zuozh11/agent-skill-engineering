# To PRD

将当前对话上下文和代码库理解合成为一份 PRD。

PRD 存放在 `docs/scratch/<NN>-<中文需求名称>/PRD.md`，其中 `NN` 记录需求进入仓库的先后顺序，中文需求名称使用 `CONTEXT.md` 中的统一术语。

PRD 按实际交付单元组织，不预设数量或类型。交付单元使用项目已有的边界名称；例如在前后端分仓项目中，可以直接命名为「前端」和「后端」。

## 流程

### 1. 加载项目上下文

使用当前任务已经由 `project-knowledge load` 返回的项目知识：用其中的 CONTEXT 术语命名，并遵守已加载的 RULE。不要在本 Skill 中自行定位领域文档或发起第二套读取流程；项目未采用知识结构或 Hook 已明确提醒知识不可用时继续执行并如实说明。

### 2. 自行查证可确认的问题

对能够通过代码、配置、现有文档或其他仓库事实确认的问题，必须先自行查证，不得把调查转交给用户；只有仓库无法确认的业务选择或外部事实才进入追问。查证过程中使用 `CONTEXT.md` 中的领域术语，并让 PRD 的 Requirements 与既有 RULES 对齐。

### 3. 追问对齐上下文

完成项目上下文加载和必要的代码确认后，先用 `grill-with-docs` 的追问流程把上下文对齐到足以产出高质量 PRD——这一步默认必跑，不预设当前上下文已经充分。

只要当前上下文尚未加载/执行过 `grill-with-docs`，就直接执行其追问流程，将确认的结论作为 PRD 输入继续后续步骤；若已执行过则跳过本步。

### 4. 确定需求编号、中文需求名称和输出路径

- 输出路径：`docs/scratch/<NN>-<中文需求名称>/PRD.md`
- `NN` 扫描 `docs/scratch/` 直属目录中匹配“开头连续数字 + 连字符”的前缀，取最大值加一，从 `01` 开始，至少两位零填充；历史无编号目录不迁移、不参与计数
- 中文需求名称从需求主题推导，优先使用 `CONTEXT.md` 中的统一术语，如 `供应商报价导出`、`交付计划变更`；不得改写为英文 slug 或拼音
- 只有明确更新既有 PRD 时才沿用原目录和编号；新需求即使名称相同也必须分配新编号
- 创建目录前重新扫描编号；如果目标目录已存在，取下一个编号重试
- 如目录不存在则创建

### 5. 确定并贯彻交付范围

交付单元是本次需求中承担独立职责且会发生改动的产品端、系统、服务或渠道。根据需求目标、业务流程、代码入口和仓库布局识别实际交付单元；事实足以确定时直接采用，无法可靠判断且不同选择会显著改变范围时使用提问工具确认。

交付单元名称必须沿用项目既有称呼：

- 前后端分仓项目可以命名为「前端」和「后端」；这里的前端、后端只是交付单元名称，不形成另一套固定分类。
- 只涉及一个交付单元时只保留该单元，不生成空章节。
- 存在多个产品端或系统时使用可区分的实际名称，如「Web 前端」「移动端」「小程序端」「业务服务」「BPM 平台」「SAP 集成」。
- 数据库、Controller、Repository 等内部技术层默认归入所属交付单元；本次不改动的外部系统作为协作依赖，不扩成当前交付范围。

按以下结构组织内容：

- **Scope**：为每个实际交付单元创建「<交付单元>范围」，列出该单元的交付内容。
- **Requirements**：先按业务能力分节；在能力内为每个实际涉及的交付单元创建「<交付单元>逻辑」，不涉及的单元不创建小节。
- **<交付单元>逻辑**：按该单元的实际职责写清交互、业务规则、状态、数据、权限、接口或流程边界，不套用预设的端类型规则。
- **协作契约**：多个单元存在调用顺序、数据交换或失败处理时统一描述，不在各单元重复维护同一约定。

交付单元及其命名必须在 Scope、Requirements 和 Implementation Decisions 中保持一致，User Stories 必须覆盖跨这些单元形成的角色目标和可观察结果。不得把多个单元的职责混写在同一组笼统条目中。

### 6. 拟草 PRD

使用下方模板。重点：
- Solution 用一个段落从用户视角概括整体解决方案，为后续交付范围和能力细节建立总览
- User Stories 要覆盖面广（numbered list）
- Requirements 按能力项组织，规则优先
- Implementation Decisions 只记录已经锁定的模块边界、接口契约、Schema 变化和关键交互，不写具体文件路径或实现代码
- 凡 Requirements 中受已加载 RULE 约束的口径，在锁定决策「来源」列标注规则完整文件名；若需求与已加载 RULE 冲突，不擅自覆盖，使用提问工具向用户确认。
- 不写代码库能力缺口对比（留给 to-task 调研阶段）

### 7. 收敛关键决策

只要仍有影响本次范围、业务规则或验收方式的关键决策未解决，必须用 `提问工具` 主动追问，不得自行假定。

每轮用户回答后立刻更新 PRD 中的对应内容。循环直到关键决策全部解决或明确排除在本次范围外。

### 8. 写入 PRD 文件

关键决策收敛后，直接将 PRD 写入 `docs/scratch/<NN>-<中文需求名称>/PRD.md`。这是本地文件写入，无需为此询问用户是否发布。

## PRD 模板

模板中的 `<交付单元>` 按项目实际名称展开。例如项目的交付单元叫「前端」「后端」，就生成「前端范围」「后端范围」和对应逻辑小节；只有一个单元时只保留一项，多单元时按事实增加。

```markdown
# <功能名称> PRD

## Solution
<用一个段落从用户视角概括整体解决方案，不展开各交付单元的实现细节>

## Scope

### <交付单元 1>范围
- <该交付单元的交付内容与职责>

### <交付单元 N>范围
- <该交付单元的交付内容与职责>

### 涉及角色
- <使用或办理本功能的角色>

## Out of Scope
<本次明确不做的内容>

## User Stories
1. As a <角色>, I want <功能>, so that <收益>
2. ...（覆盖面要广）

## Requirements
### <能力项 1>

#### <交付单元 1>逻辑
- <该交付单元承担的行为、规则、状态、数据与边界>

#### <交付单元 N>逻辑
- <该交付单元承担的行为、规则、状态、数据与边界>

#### 协作契约
- <仅在多个交付单元存在调用顺序、数据交换或失败处理时保留>

### <能力项 2>

...

## Implementation Decisions
### 锁定决策
| 决策项 | 决策值 | 来源 |
|---|---|---|
| ... | ... | 用户确认 / RULES / PRD |

```

## 质量要求

- 检查交付单元是否与实际范围一致且数量完整，名称是否沿用项目已有称呼；单个交付单元不生成空章节，多个交付单元不遗漏实际参与交付的单元
- 检查 Scope、Requirements 和 Implementation Decisions 中的交付单元名称与边界是否一致；每个能力项只包含实际涉及的交付单元
- 每个「<交付单元>逻辑」只描述该单元的实际职责，不得在同一条目中混写多个单元职责，也不得根据单元名称套用未经查证的职责
- 多个交付单元存在调用顺序、数据交换或失败处理时，检查「协作契约」是否完整且没有在各单元重复维护冲突口径
- Requirements 以规则优先，先写规则再补功能
- 对关键口径做「可实施性精度」自检：字段清单是否完整、日期/状态/编号是否有明确时机和值
- 不伪造已确认事实；影响本次交付且无法确认的内容必须先向用户追问
- 不写实现流水账、技术建议或改造建议
- 使用 CONTEXT.md 中定义的术语，不漂移到同义词
