# 疑难诊断方法

在现有证据不足以区分原因时选择需要的方法；各方法独立使用，顺序由问题决定。

## 建立可重复观察

优先复用实际失败的测试、请求、SQL、CLI 调用或日志。需要重复实验时，把触发输入和能区分结果的观察整理成一个紧凑命令。

自动化成本与调查需要相称：已有调用能说明问题时直接使用；需要浏览器操作、trace 回放或隔离依赖时再构造相应工具。观察需要覆盖用户报告的症状，而不只是检查运行没有报错。

Agent 无法执行、确实需要用户操作的步骤，可使用 [hitl-loop.template.sh](./scripts/hitl-loop.template.sh) 收集观察结果。缺少可重复命令时仍可利用现有代码、数据和日志缩小范围。

## 最小化与回归比较

输入或环境复杂、难以区分原因时，逐步移除无关因素，并确认观察到的仍是原故障。缩小到足以判断原因即可，不要求证明每个剩余元素都不可删除。

已有明确的正常与异常版本时，可使用差异比较或 `git bisect`；这类操作应在不会覆盖用户工作的隔离环境中进行。

## 间歇性故障

记录失败频率、输入和时序。根据证据选择重复运行、固定随机种子、增加并发或调整时序，让候选原因的差异更容易观察。试验强度与环境承受能力相称，不设统一次数或复现率门槛。

## 插桩

让每个探针回答一个具体问题：优先使用现有调试器、查询或定向日志。尽量一次改变一个关键因素，并记录变化与观察结果。

需要临时日志时使用可检索的唯一标签，调查结束后移除。对应用、数据和环境的修改沿用当前任务授权；生产插桩需要覆盖该操作的明确授权。

## 性能问题

先确认慢在哪里：耗时分布、请求链路、查询计划或 profiler。使用可比较的负载与环境，针对测量暴露的瓶颈调查；只有结果需要区分波动时才增加重复测量。

## 固化证据

根因得到支持后，选择能覆盖真实触发路径的验证方式。可维护且有实际回归价值的复现保留为测试；一次性调查工具按任务需要删除或存放在明确的调试位置。
