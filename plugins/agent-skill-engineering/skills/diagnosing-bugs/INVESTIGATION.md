# 疑难诊断方法

现有证据不足以区分原因，或故障难复现、间歇出现、属于性能回退时使用。核心是一个紧凑的 pass/fail 信号：_这个_ bug 出现时变红。二分、假设检验和插桩都只消费这个信号。

## 建立能变红的循环

优先复用实际失败的测试、请求、SQL、CLI 调用或日志。需要重复实验时，把触发输入和能区分结果的观察整理成一个紧凑命令。大致按此顺序尝试：

1. **失败测试**——在能触及 bug 的任何接缝处：单元、集成、端到端。
2. **Curl / HTTP 脚本**——对运行中的开发服务器发请求。
3. **CLI 调用**——用固定输入，将 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**——驱动 UI，对 DOM、控制台或网络做断言。
5. **回放捕获的 trace**——将真实请求或事件日志保存到磁盘，在隔离环境中回放。
6. **一次性测试工具**——启动系统的最小子集，用单个调用执行 bug 代码路径。
7. **属性 / 模糊循环**——bug 是「有时输出错误」时，用随机输入寻找失败模式。
8. **二分或差异循环**——两个已知状态之间出现的 bug，自动化切换并比较输出。
9. **HITL bash 脚本**——必须由人点击时，用 [hitl-loop.template.sh](./scripts/hitl-loop.template.sh) 收集观察。

自动化成本与调查需要相称：已有调用能说明问题时直接使用。观察必须覆盖用户报告的症状，而不只是检查运行没有报错。

循环还要更快、信号更清晰、更确定性：缓存 setup，断言具体症状，固定时间、随机种子和外部依赖。一个 30 秒的不稳定循环几乎和没有循环一样差。

间歇性故障的目标不是干净复现，而是足够高的复现率。根据证据选择重复运行、固定随机种子、增加并发或调整时序；试验强度与环境承受能力相称。

确实无法建立循环时停下来说明已尝试的方法，向用户请求可复现环境、捕获制品，或生产插桩授权。没有循环时不要继续假设。

### 完成标准

指出一个已经实际运行过至少一次的命令，并展示调用和输出：

- **能变红**——执行真实 bug 代码路径并断言用户描述的确切症状。
- **确定性**——每次运行得出相同判定；非确定性 bug 则固定足够高的复现率。
- **快速**——以秒而非分钟计。
- **Agent 可运行**——可无人值守运行；仅允许通过 HITL 脚本引入人工操作。

建立这个命令前，只为定位运行方式、复现入口与可测试接缝而有限阅读代码。不得据此锁定根因。没有能变红的命令，不得进入最小化或假设。

## 复现与最小化

运行循环。确认失败模式就是用户描述的那一个，并捕获确切症状。

循环变红后，把复现缩减为仍然变红的最小场景。每次只删除一项输入、调用者、配置、数据或操作步骤，随后重新运行；只保留触发失败不可缺少的元素。缩小到足以判断原因即可。

已有明确的正常与异常版本时，可使用差异比较或 `git bisect`；这类操作应在不会覆盖用户工作的隔离环境中进行。

## 假设

在测试任何假设之前，生成 3 到 5 个排序的可证伪假设。每个假设陈述预测：

> 如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更严重。

无法陈述预测的假设只是直觉，丢弃或锐化它。向用户展示排序列表，但不要阻塞等待；用户不在就按你的排序继续。

## 插桩

每个探针必须映射到一个具体预测。一次只改变一个变量。优先使用现有调试器、查询或定向日志；需要临时日志时使用可检索的唯一标签，如 `[DEBUG-a4f2]`，调查结束后移除。

对应用、数据和环境的修改沿用当前任务授权；生产插桩需要覆盖该操作的明确授权。

## 性能问题

日志通常是错误的工具。先确认慢在哪里：耗时分布、请求链路、查询计划或 profiler。使用可比较的负载与环境，针对测量暴露的瓶颈调查；只有结果需要区分波动时才增加重复测量。
