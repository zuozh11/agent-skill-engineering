# Diagnosing Bugs

一套针对疑难 bug 的纪律。只有在明确说明理由时才能跳过阶段。

探索代码库时，使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。用已加载术语建立相关模块的心智模型。

## 阶段 1 — 建立反馈循环

核心是一个紧凑的 pass/fail 信号：_这个_ bug 出现时变红。二分、假设检验和插桩都只消费这个信号；没有它，读代码定位不了根因。在这里投入不成比例的精力。

### 构建反馈循环的方法——大致按此顺序尝试

1. **失败测试**——在能触及 bug 的任何接缝处：单元、集成、端到端。
2. **Curl / HTTP 脚本**——对运行中的开发服务器发请求。
3. **CLI 调用**——用固定输入，将 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络做断言。
5. **回放捕获的 trace。** 将真实的网络请求/载荷/事件日志保存到磁盘；在隔离环境中通过代码路径回放。
6. **一次性测试工具。** 启动系统的最小子集（一个服务，mock 依赖），用单个函数调用来执行 bug 代码路径。
7. **属性/模糊循环。** 如果 bug 是「有时输出错误」，运行 1000 个随机输入寻找失败模式。
8. **二分工具。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化「在状态 X 启动，检查，重复」以便 `git bisect run`。
9. **差异循环。** 对同一输入分别通过旧版本和新版本（或两种配置）运行并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人来点击，用 `scripts/hitl-loop.template.sh` 来驱动_他们_，使循环仍然结构化。捕获的输出反馈给你。

建立正确的反馈循环，bug 就已经解决了 90%。

### 迭代循环本身

把循环当作产品来对待。一旦有了一个循环，问：

- 能更快吗？（缓存 setup，跳过无关初始化，缩小测试范围。）
- 能让信号更清晰吗？（断言具体症状，而不是「没崩溃」。）
- 能更确定性吗？（固定时间，设定随机种子，隔离文件系统，冻结网络。）

一个 30 秒的不稳定循环几乎和没有循环一样差。目标是秒级、确定性的循环。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次，并行化，加压力，缩小时间窗口，注入 sleep。50% 复现率可调试；1% 不够——持续提高直到可调试。

### 当你确实无法建立循环时

停下来明确说明。列出你尝试过的方法。向用户请求：(a) 访问能复现的环境，(b) 捕获的制品（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时生产环境插桩。没有循环时不要继续假设。

### 完成标准——能变红的紧凑循环

阶段 1 仅当反馈循环既**紧凑**又**能变红**时完成：指出一个已经实际运行过至少一次的命令——脚本路径、测试命令或 curl——并展示调用和输出。它必须同时满足：

- [ ] **能变红**——执行真实的 bug 代码路径并断言用户描述的确切症状，因此能在这个 bug 存在时变红、修复后变绿。仅仅「运行时没有报错」不算。
- [ ] **确定性**——每次运行得出相同判定；非确定性 bug 则按上文固定一个足够高的复现率。
- [ ] **快速**——以秒而非分钟计。
- [ ] **Agent 可运行**——可无人值守地运行；仅允许通过 `scripts/hitl-loop.template.sh` 引入人工操作。

建立这个命令前，允许有限阅读项目说明、测试配置、入口文件和相关调用路径，以定位运行方式、复现入口与可测试接缝。此时阅读的目标只能是建立反馈循环，不得据此生成或锁定根因理论；如果开始大范围阅读并猜测原因，立即回到反馈循环。没有能变红的命令，不得进入阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。观察 bug 出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是恰好在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者对于非确定性 bug，复现率足够高以支持调试）。
- [ ] 已捕获确切症状（错误消息、错误输出、慢响应时间），以便后续阶段验证修复确实解决了它。

### 最小化

循环变红后，把复现缩减为仍然变红的**最小场景**。每次只删除一项输入、调用者、配置、数据或操作步骤，随后重新运行循环；只保留触发失败不可缺少的元素。

最小复现会缩小阶段 3 的假设空间，并成为日后回归测试的种子。当剩余的每个元素都不可缺少——删除任意一个都会让循环变绿——最小化才完成。完成复现和最小化之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前，生成 **3 到 5 个排序的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式：「如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更严重。」

无法陈述预测的假设只是直觉——丢弃或锐化它。

**在测试之前向用户展示排序列表。** 他们通常有领域知识可以立即重新排序，或知道已经排除的假设。不要阻塞等待——用户不在就按你的排序继续。

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 中的一个具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**——如果环境支持。一个断点胜过十条日志。
2. **定向日志**——在区分假设的边界处。
3. 定向记录，不为事后检索而全量打日志。

**给每条调试日志打标签**，使用唯一前缀，如 `[DEBUG-a4f2]`，以便修复阶段一次 `grep` 清理。

**性能分支。** 对于性能回退，日志通常是错误的工具。改为：建立基线测量（计时工具、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 诊断交付

阶段 4 完成后，向用户交付复现方式、根因证据、影响范围与最小修复建议。

用户明确要求「修复」「解决」或实现改动时，完整读取 [FIX.md](./FIX.md) 并继续。只要求诊断时，移除阶段 4 添加的临时插桩和一次性制品后停止。意图不明时，在任何修复性写入前提问确认。
