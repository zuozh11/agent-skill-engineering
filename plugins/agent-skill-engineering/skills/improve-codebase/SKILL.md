# Improve Codebase

一次性只读审计代码库，输出可以直接删除、替换或收回明确所有者的精简清单。不生成文件，不修改代码，不进入决策或实施流程。

## 范围

使用已加载的 CONTEXT 术语与 RULE；尚未加载则按项目知识协议执行，知识不可用时继续并说明。

- 用户指定模块、目录或痛点时，完整扫描该范围。
- 用户未指定时，扫描整个仓库的生产代码、依赖清单和注册入口。
- 排除生成代码、vendored 代码、构建产物和明确的测试 fixture，并在结果中列出排除项。

## 查找

理解入口、消费者和真实调用路径，查找：

- 无消费者代码、死分支、废弃 flag、无人设置的配置和推测性能力；
- 单实现接口、单产品工厂、只转发 wrapper、单导出文件和未来扩展点；
- 重复 helper、类型、状态或项目已有惯用法的第二套实现；
- 手写标准库能力，或重复浏览器、数据库、运行时和框架原生能力的代码与依赖；
- 新依赖只完成少量朴素代码，或已安装依赖已经提供相同能力；
- 相同行为可以用更少文件和概念直接表达的实现；
- 不可删除的共同业务规则散落在多个调用者，缺少明确所有者。

对每个发现停在第一项成立的处理方式：

1. `delete`：删除且不替代；
2. `reuse`：改用代码库现有所有者；
3. `stdlib`：改用具体标准库能力；
4. `native`：改用具体平台原生机制；
5. `dependency`：复用已安装依赖，不增加新依赖；
6. `shrink`：用更少文件和概念保持相同行为；
7. `owner`：前六项都不能解决时，把共同规则收回现有所有者；没有合适所有者时才建议最小新所有者。

一个发现只保留最高的可行处理方式。`owner` 候选读取 `codebase-design` 并通过其所有权门槛；不通过就不报告。

## 证据边界

只报告能够从当前代码证明的发现：必须确认真实消费者、动态注册、外部契约和删除后的可观察行为。消费者或兼容性不明时不猜测，也不降级为低置信度建议。

不建议删除用户显式要求、项目 RULE、信任边界校验、安全、无障碍或防止数据丢失的必要行为。不把正确性缺陷、业务规则偏差和性能问题混入本审计。

## 排序与输出

按实际减少的维护责任排序；收益相当时按 `delete → reuse → stdlib → native → dependency → shrink → owner` 排序。不估算 LOC，不为凑数量输出意见。

```markdown
审计范围：<目录、生产入口和依赖清单>
排除：<生成、vendored、构建产物和 fixture>

1. delete: <删除什么>；<成立证据>。[`path:line`]
2. reuse: <哪套重复实现>；改用 <现有所有者>。[`path:line`]
3. native: <自建能力或依赖>；改用 <平台机制>。[`path:line`]
4. owner: <散落的共同规则>；收回 <现有或最小所有者>。[`path:line`]

汇总：delete <N>，reuse <N>，stdlib <N>，native <N>，dependency <N>，shrink <N>，owner <N>。
```

没有可信发现时只输出「当前范围未发现可证明的过度设计或可删除复杂度」。输出后停止；用户要求实施时再单独进入 `impl`。
