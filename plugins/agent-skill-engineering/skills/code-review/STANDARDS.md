# Standards 评审

只在启用 Standards 时读取。输入为固定代码范围、项目 RULE、Agent 工程指令和最小实现阶梯；不接收业务需求材料或 Spec 结论。

## 项目规范

按项目知识协议使用相关 CONTEXT。启用 Standards 时先稳定枚举项目提供的全部 RULE 文件，记录每个 RULE 的原始标题、路径和顺序，得到 RULE 清单与总数 `R`。随后从头到尾读取清单中的每个文件；索引、摘要、搜索命中、历史记忆和只读标题都不能代替正文。

本 Skill 中，项目 `RULE` 指项目知识协议加载的规范文件，全部归入 Standards；即使某条 `RULE` 提到状态、数据、校验、权限或业务流程，也仍是项目规范，不进入 Spec。业务规则指 PRD、API 清单、任务卡、Issue 和当前对话中的已确认要求，只归入 Spec，不进入 Standards。历史或被当前明确要求取代的材料不作为评审依据。

任一 RULE 无法枚举、打开或读完时，Standards 尚未开始。只报告读取失败的路径或缺口，不输出部分评审结果。

## 检查

读取范围内生效的 `AGENTS.md`、`CLAUDE.md`、项目完整 RULE 集合，以及用户明确指定的其他工程规范。PRD、任务卡等需求不进入 Standards。记录每个来源的路径、准确标题和具体条款；没有明确来源的观点不是评审依据。

调用方给出的候选 `ruleId` 全部进入 Standards 的 RULE 清单，但候选列表不能替代或缩小项目完整 RULE 集合。

先建立完整评审范围清单：记录全部文件及 changed hunk；snapshot 模式记录全部目标文件及其中需要审查的代码段。得到代码段总数 `H`。范围较大时可以稳定分批，但每个批次都属于同一次评审，不能只审“重点路径”或抽样。

### RULE 逐条核对

按照 RULE 清单顺序逐个处理。对一个 RULE，先把该 RULE 的完整正文与完整评审范围逐段对照，完成后才处理下一个 RULE。不按关键词、文件名或主观相关性预筛。每个 RULE 的原始标题在最终表中必须且只能出现一次，并判定为：

- `违反`：固定范围内有代码直接违反具体条款；
- `符合`：至少一个条款适用于固定范围，完整核对后没有发现违反；
- `不适用`：整个 RULE 约束的技术、模块或场景都未出现在固定范围，原因必须可复核。

只要一个适用条款违反，整条 RULE 判为 `违反`，并在同一行列全该 RULE 的所有违反证据。存在适用条款时不能判为 `不适用`。`违反`必须同时给出 RULE 的路径与具体条款、代码位置、违反原因和大致修改方向；不能指出具体条款或代码证据时，继续核实，不能生成问题。

### 必要性审查

完整读取 [MIN-IMPL.md](../codebase-design/MIN-IMPL.md)。对范围清单中的每个 changed hunk 及其完整 enclosing symbol 逐段回答：

1. 这段代码具体做什么，服务哪个已确认行为或真实调用者？
2. 它必须存在吗；删除后，已确认行为是否仍然成立？
3. 删除、复用现有代码、标准库、平台原生能力或已安装依赖，能否让实现更简单？
4. 删除或替换后，文件、类型、分支、状态和概念的净数量是减少还是增加？

如果删除后行为仍正确且实现更简单，这段代码违反 `MIN-IMPL.md`，应当删除。如果必须用更复杂的实现才能维持正确行为，则保留。只有能够说明真实调用路径、删除前后行为和净复杂度变化时，才能报告必要性问题；猜测未来扩展、泛泛代码味道、个人偏好和“也许更优雅”都不构成问题来源。

修复缺陷时检查待修改位置的全部调用者；共同根因能够在真实所有者修复时，把散落在调用者的补丁作为 `MIN-IMPL.md` 违反报告。`codebase-design` 只在已证明确有必要调整模块形状时读取。

每审完一个代码段就在内部范围清单标记一次；必须达到 `H/H`。必要性问题统一归入表中的 `最小实现阶梯 / MIN-IMPL.md` 行。任何问题缺少明确来源或具体证据时删除该问题，不影响继续完成剩余 RULE 和代码段。

## 终检

主 Agent 维护并终检两份账本：RULE 清单 `R` 条和代码段清单 `H` 段。输出前必须同时满足：

- Standards 表中的项目 RULE 行数等于 `R`；
- 表中 RULE 标题集合与清单完全相等，顺序一致、没有重复；
- 每行判定只能是 `符合`、`违反`、`不适用`；
- 代码段清单全部完成，达到 `H/H`；
- 每个违反都能定位到具体 RULE 条款和代码证据。

任一条件未满足时继续补齐。因外部缺口确实无法继续时，只输出 `Standards 评审未完成`、已完成数量和具体缺口；不得输出违反清单、通过结论或任何部分 RULE 表。

保留问题前确认位置准确、影响具体、依据属于本维度，建议是最小正确方向。

## 输出

Standards 表必须按清单顺序包含项目全部 RULE 的原始标题，每个标题恰好一行。一个 RULE 有多个违反时全部写在同一行。其他工程规范和 `最小实现阶梯 / MIN-IMPL.md` 各自最多增加一行；没有明确来源的问题不输出。Standards 的任何结果都写在这张表中，不在表后追加“补充核实”、遗漏项、额外 finding 或部分覆盖声明。

```markdown
评审范围：<固定点、diff 命令和路径>

## Standards

| Rule 标题 | 判定 | 源头 | 代码证据 | 原因 | 大致修改方向 |
|---|---|---|---|---|---|
| `<原始标题>` | `符合 / 违反 / 不适用` | `<来源路径:行，具体条款>` | `<全部违反的代码路径:行；无则 —>` | `<判定理由>` | `<违反时写最小方向；否则 —>` |
| 最小实现阶梯 / MIN-IMPL.md | `符合 / 违反 / 不适用` | `codebase-design/MIN-IMPL.md:<行，具体条款>` | `<全部违反的代码路径:行；无则 —>` | `<用途、真实调用者、删除前后行为及净复杂度变化>` | `<违反时写删除或更简单的替代；否则 —>` |

```

表后只写一行结论：`Standards：已完成 R/R 条 RULE、H/H 个代码段；通过 / 存在 N 条违反`。不得用“重点路径已审”“其余需补充”“主审后续合并”等措辞结束。没有违反时也必须保留完整 RULE 表，不制造改进意见，不估算净减少行数。
