# Code Review

对固定代码范围执行双轴只读评审：

- **Standards**：代码是否符合仓库记录的工程规范？
- **Spec**：代码是否忠实实现了需求来源？

两个维度由相互独立的子 Agent 并行评审，再分栏聚合，避免彼此上下文污染和结论遮蔽。本 Skill 只报告问题，不修改代码、提交或远端状态。

## 流程

### 1. 加载项目上下文

使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。

记录本次加载的 CONTEXT 与 RULE 来源。相关 CONTEXT 提供给 Standards Agent 和 Spec Agent，完整 RULE 提供给 Standards Agent，并由主 Agent 在聚合前逐条终检。评审范围扩大时，按新的完整范围重新加载项目知识。

### 2. 固定评审范围

把用户指定的 commit、branch、tag 或 range 作为固定点，先验证引用存在。分支范围使用 `git diff <fixed-point>...HEAD`，并记录 `git log <fixed-point>..HEAD --oneline`。

用户未明确给出固定点时，根据请求选择可复现范围：

- PR 编号或 URL：使用代码托管连接器或 CLI 解析真实 base、head 和 patch；
- 当前分支：检查上游分支和默认分支，能够确定时使用 merge-base，否则提问；
- 未提交改动：同时固定未暂存、已暂存和未跟踪文件；
- 文件或目录的当前实现：完整读取 [SNAPSHOT.md](./SNAPSHOT.md) 固定文件列表和工作区状态。

用户同时指定路径时，用同一 pathspec 限制整个范围。引用无效、diff 为空或 snapshot 没有有效文件时停止，不启动子 Agent。

### 3. 定位 Spec 来源

按以下顺序查找需求依据：

1. 用户明确指定的 PRD、API 清单、任务卡、Issue、PR 或当前对话目标；
2. commit 消息或变更内容引用的需求来源；
3. 与需求目录、分支名称或变更主题明确对应的本地需求文档。

读取真实存在的完整内容，不根据文件名猜测。没有可用需求来源时跳过 Spec Agent，并在最终报告中标明「无可用需求依据」。

### 4. 定位 Standards 来源

读取当前范围生效的 `AGENTS.md`、`CLAUDE.md` 或等效 Agent 指令，以及仓库中的编码规范、测试约定和模块约束。项目明确记录的规范始终优先；工具能够确定性检查的问题交给工具。

在项目规范之上，Standards 始终使用以下代码味道基线。它们是需要证据和判断的风险信号，不是硬性违规；项目规范明确认可某种写法时不报告对应信号。

- **含义不明的名称（Mysterious Name）**：名称无法说明其持有的数据或行为。改成诚实名称；无法命名通常说明设计仍不清楚。
- **重复代码（Duplicated Code）**：同一逻辑形态出现在多个改动位置。提取共享形态并复用。
- **Feature Envy**：方法操作另一个对象的数据多于自身数据。把行为移到它依赖的数据一侧。
- **Data Clumps**：同一组字段或参数反复一起传递。将它们组合成一个明确类型。
- **Primitive Obsession**：字符串或数字承载应有独立约束的领域概念。为该概念建立类型。
- **重复分支（Repeated Switches）**：围绕同一类型或状态的分支在多处重复。集中为一个映射或多态行为。
- **Shotgun Surgery**：一个逻辑变化迫使大量位置同步修改。把共同变化集中到一个模块。
- **Divergent Change**：同一模块因多个无关原因变化。按变化原因拆开职责。
- **Speculative Generality**：为当前需求不存在的未来场景增加抽象、参数或扩展点。删除并收回到真实需求。
- **Message Chains**：调用者依赖过长的对象导航链。把导航隐藏在首个对象提供的方法后。
- **Middle Man**：模块主要透传调用，没有隐藏复杂度。移除无价值的中间层。
- **Refused Bequest**：子类或实现忽略、拒绝继承的大部分行为。移除不合适的继承，改用组合。

当前范围涉及模块职责、接口表面积、接缝、adapter、测试面或深浅程度时，读取 `codebase-design` 并把其判断准则交给 Standards Agent。

### 5. 并行执行两个维度

并行创建 Standards Agent 和 Spec Agent。两者接收相同的固定范围与 commit 列表，但不读取对方的中间结论，也不修改文件。

**Standards Agent** 同时接收：

- 项目规范来源；
- 上述完整代码味道基线；
- 已加载的 RULE；
- 本次决定加载的 `codebase-design` 判断准则。

它逐文件或 hunk 报告项目规范违反和具有实际影响的风险信号。每条 finding 引用规范或命名风险信号，并提供紧凑代码位置和具体影响；明确区分硬性违反与判断性提示，跳过工具已经检查的事项。

**Spec Agent** 接收完整需求来源和相关 CONTEXT，报告：

- 缺失或只完成一部分的需求；
- 需求未要求的 scope creep；
- 看似已实现但行为错误的需求。

每条 finding 必须引用对应需求依据。没有 Spec 来源时不创建 Spec Agent。

### 6. RULE 终检

聚合前，主 Agent 亲自把已加载的全部 RULE 与完整评审范围逐条对照，标记为符合、不适用或违反，并保留文件与行号证据。Standards Agent 漏报的违反补入 Standards；无法完成终检时明确说明，不能宣称 Standards 通过。

最终报告列出本次覆盖的 RULE 文件，并把终检标为「通过」「存在上述违反」或「未完成」。

### 7. 聚合

在 `## Standards` 和 `## Spec` 下分别呈现两份报告，只做轻度文字清理，不跨维度合并或重排 finding。

每条 finding 使用 `P0` 到 `P3`：`P0` 阻断交付或造成重大事故，`P1` 高概率导致错误行为，`P2` 局部缺陷或明显维护风险，`P3` 低风险改进。使用以下格式：

```markdown
评审范围：<固定点、diff 命令与路径；或 snapshot 的 HEAD、路径和文件数>

## Standards

- [P1] <问题标题> — `<文件:行>`
  - 证据：<项目规范或风险信号>
  - 影响：<实际风险>
  - 建议：<最小修复方向>

RULE 终检：已覆盖 <RULE 文件列表>；<通过 / 存在上述违反 / 未完成>

## Spec

- [P1] <问题标题> — `<文件:行>`
  - 需求依据：<对应需求条目>
  - 偏差：<遗漏、错误、scope creep 或验收缺口>
  - 建议：<最小修复方向>
```

没有发现时明确写「未发现问题」，不为填充报告制造意见。最后用一行分别汇总两个维度的 finding 数量及各自最严重的问题，不选出跨维度的单一赢家。

## 为什么分成两个维度

一个改动可以通过一侧而在另一侧失败：

- 完全符合编码规范，却实现了错误需求：**Standards 通过，Spec 失败**。
- 完全实现需求，却违反项目约定：**Spec 通过，Standards 失败**。

分开报告可以防止一个维度掩盖另一个维度。
