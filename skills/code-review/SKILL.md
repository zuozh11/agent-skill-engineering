# Code Review

对固定代码范围执行只读评审：

- **Standards**：只判断代码是否违反项目工程规范。
- **Spec**：只判断实现是否违反已确认的业务规则。

`--std` 只评审 Standards，`--spec` 只评审 Spec；不传参数或同时传入两个参数时评审两个维度。两个维度只共享固定代码范围，不共享评审依据：项目工程规范不得产生 Spec finding，业务规则不得产生 Standards finding。同一个问题不得跨维度重复报告。两个维度同时启用时，由相互独立的子 Agent 并行评审，再分栏聚合。本 Skill 只报告问题，不修改代码、提交或远端状态。

## 流程

### 1. 加载项目上下文

使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。

记录本次加载的 CONTEXT 与 RULE 来源，并按约束对象分开：约束代码结构、写法、测试或工程协作的是项目工程规范；约束系统行为、状态、数据、校验、权限或业务流程的是业务规则。每条依据只进入对应维度。评审范围扩大时，按新的完整范围重新加载项目知识。

### 2. 固定评审范围

把用户指定的 commit、branch、tag 或 range 作为固定点，先验证引用存在。分支范围使用 `git diff <fixed-point>...HEAD`，并记录 `git log <fixed-point>..HEAD --oneline`。

用户未明确给出固定点时，根据请求选择可复现范围：

- PR 编号或 URL：使用代码托管连接器或 CLI 解析真实 base、head 和 patch；
- 当前分支：检查上游分支和默认分支，能够确定时使用 merge-base，否则提问；
- 未提交改动：同时固定未暂存、已暂存和未跟踪文件；
- 文件或目录的当前实现：完整读取 [SNAPSHOT.md](./SNAPSHOT.md) 固定文件列表和工作区状态。

用户同时指定路径时，用同一 pathspec 限制整个范围。引用无效、diff 为空或 snapshot 没有有效文件时停止，不启动子 Agent。

### 3. 定位 Spec 来源

仅启用 Spec 时执行本节。

按以下顺序查找需求依据：

1. 用户明确指定的 PRD、API 清单、任务卡、Issue、PR 或当前对话目标；
2. 已加载项目知识中的业务 RULE 与相关 CONTEXT；
3. commit 消息或变更内容引用的需求来源；
4. 与需求目录、分支名称或变更主题明确对应的本地需求文档。

读取真实存在的完整内容，不根据文件名猜测，不把当前代码、工程惯例或代码味道转成业务规则。没有可用业务规则来源时跳过 Spec Agent，并在最终报告中标明「无可用业务规则依据」。

### 4. 定位 Standards 来源

仅启用 Standards 时执行本节。

读取当前范围生效的 `AGENTS.md`、`CLAUDE.md` 或等效 Agent 指令，以及仓库中的编码规范、测试约定、模块约束和已加载项目知识中的工程规范。项目明确记录的规范始终优先；工具能够确定性检查的问题交给工具。PRD、任务卡、用户故事、验收条件和业务 RULE 不进入 Standards。

在项目规范之上，Standards 始终使用以下代码味道基线。它们是需要证据和判断的风险信号，不是硬性违规；项目规范明确认可某种写法时不报告对应信号。

- **含义不明的名称（Mysterious Name）**：名称无法说明其持有的数据或行为。改成诚实名称；无法命名通常说明设计仍不清楚。
- **重复代码（Duplicated Code）**：同一逻辑形态出现在多个改动位置。提取共享形态并复用。
- **Feature Envy**：方法操作另一个对象的数据多于自身数据。把行为移到它依赖的数据一侧。
- **Data Clumps**：同一组字段或参数反复一起传递。将它们组合成一个明确类型。
- **Primitive Obsession**：字符串或数字承载应有独立约束的领域概念。为该概念建立类型。
- **重复分支（Repeated Switches）**：围绕同一类型或状态的分支在多处重复。集中为一个映射或多态行为。
- **Shotgun Surgery**：一个逻辑变化迫使大量位置同步修改。把共同变化集中到一个模块。
- **Divergent Change**：同一模块因多个无关原因变化。按变化原因拆开职责。
- **Speculative Generality**：为当前需求不存在的未来场景增加抽象、参数或扩展点。删除并收回到真实需求。
- **Message Chains**：调用者依赖过长的对象导航链。把导航隐藏在首个对象提供的方法后。
- **Middle Man**：模块主要透传调用，没有隐藏复杂度。移除无价值的中间层。
- **Refused Bequest**：子类或实现忽略、拒绝继承的大部分行为。移除不合适的继承，改用组合。

当前范围涉及模块职责、接口表面积、接缝、adapter、测试面或深浅程度时，读取 `codebase-design` 并把其判断准则交给 Standards Agent。

### 5. 执行所选维度

为每个已启用维度创建对应 Agent；两个维度同时启用时并行创建。两者只接收相同的固定范围与 commit 列表，各自只接收本维度依据，不读取对方的依据或中间结论，也不修改文件。

**Standards Agent** 同时接收：

- 项目规范来源；
- 上述完整代码味道基线；
- 已加载项目知识中的工程规范；
- 本次决定加载的 `codebase-design` 判断准则。

它把全部项目工程规范与完整评审范围逐条对照，标记「符合」「不适用」或「违反」，保留文件与行号证据，并向主 Agent 返回逐条核对表；任一工程规范未核对时，Standards 评审视为未完成。随后逐文件或 hunk 报告项目工程规范违反和具有实际影响的风险信号。每条 finding 引用工程规范或命名风险信号，并提供紧凑代码位置和具体影响；明确区分硬性违反与判断性提示，跳过工具已经检查的事项。需求遗漏、业务行为错误和 scope creep 不得作为 Standards finding。

**Spec Agent** 只接收完整业务规则来源和相关 CONTEXT，报告：

- 缺失或只完成一部分的需求；
- 需求未要求的 scope creep；
- 看似已实现但行为错误的需求。

每条 finding 必须引用对应业务规则依据。命名、重复、架构、代码风格、测试写法或其他工程质量问题不得作为 Spec finding。没有业务规则来源时不创建 Spec Agent。

### 6. 主 Agent 分轴复核

聚合前，主 Agent 独立复核每个已启用 Agent 的每条候选 finding：重新读取所引代码和本维度依据，必要时追踪相关调用路径，只保留能由固定评审范围直接证明且具有具体影响的问题。删除证据不足、依赖未验证假设、超出范围、实际不成立或使用另一维度依据的候选；不把跨维度候选改名后保留。根据复核结果修正问题表述、代码位置和建议，并独立判定严重程度，可以上调或下调子 Agent 给出的 `P0` 到 `P3`。复核不是原样转发；未完成逐条复核时不输出最终报告。

启用 Standards 时，主 Agent 再确认 Standards Agent 的逐条核对覆盖了全部项目工程规范，并亲自与完整评审范围逐条对照。启用 Spec 时，主 Agent 再确认 Spec Agent 覆盖了全部已确认业务规则，并亲自与完整评审范围逐条对照。各自标记为符合、不适用或违反，保留文件与行号证据；漏核时补做，漏报的违反补入对应维度。

最终报告仅为已启用维度列出对应依据的逐条覆盖状态，并把主 Agent 终检标为「通过」「存在上述违反」或「未完成」。

### 7. 聚合

仅为已启用维度输出对应的 `## Standards` 或 `## Spec`，呈现主 Agent 复核后保留的问题，不输出已删除的候选，也不跨维度合并 finding。

每条保留 finding 都分配一个在本次报告中唯一、连续且便于引用的编号：Standards 使用 `STD-001`、`STD-002`，Spec 使用 `SPEC-001`、`SPEC-002`。编号在完成过滤和排序后生成。严重程度使用主 Agent 最终判定的 `P0` 到 `P3`：`P0` 阻断交付或造成重大事故，`P1` 高概率导致错误行为，`P2` 局部缺陷或明显维护风险，`P3` 低风险改进。使用以下格式：

```markdown
评审范围：<固定点、diff 命令与路径；或 snapshot 的 HEAD、路径和文件数>

## Standards（仅启用 Standards 时）

- [STD-001] [P1] <问题标题> — `<文件:行>`
  - 证据：<项目规范或风险信号>
  - 影响：<实际风险>
  - 建议：<最小修复方向>

项目规范核对：Standards 已逐条覆盖 <项目工程规范列表 / 未完成>；主 Agent 终检 <通过 / 存在上述违反 / 未完成>

## Spec（仅启用 Spec 时）

- [SPEC-001] [P1] <问题标题> — `<文件:行>`
  - 业务依据：<对应业务规则>
  - 偏差：<遗漏、错误、scope creep 或验收缺口>
  - 建议：<最小修复方向>

业务规则核对：Spec 已逐条覆盖 <业务规则列表 / 未完成>；主 Agent 终检 <通过 / 存在上述违反 / 未完成>
```

没有发现时明确写「未发现问题」，不为填充报告制造意见。最后用一行分别汇总已启用维度复核后保留的 finding 数量，并通过编号引用各自最严重的问题；两个维度同时启用时不选出跨维度的单一赢家。

## 为什么分成两个维度

一个改动可以通过一侧而在另一侧失败：

- 完全符合项目工程规范，却违反业务规则：**Standards 通过，Spec 失败**。
- 完全符合业务规则，却违反项目工程规范：**Spec 通过，Standards 失败**。

分开报告可以防止一个维度掩盖另一个维度。
