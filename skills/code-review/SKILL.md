# Code Review

对固定的代码范围执行只读评审，分别回答两个问题：

- **Standards**：评审范围是否符合仓库记录的编码约束、项目规则和高置信度代码质量基线？
- **Spec**：评审范围是否完整、准确地实现了 PRD、任务卡或当前对话确定的需求？

两个维度必须独立调查、独立报告，不能让一个维度的结论掩盖另一个维度的问题。本 Skill 只报告问题，不修改代码；用户后续明确要求修复时再进入实现流程。

## 流程

### 1. 固定评审范围

默认优先把评审范围解析为可重复执行的 diff：

- 用户指定 commit、branch、tag 或 range 时，直接使用并先验证引用真实存在。
- 用户指定 PR 编号或 URL 时，优先使用可用的代码托管连接器或 CLI 只读解析其 base/head 与 patch；当前宿主无法读取时明确报告，不根据编号猜测范围。
- 用户明确要求评审未提交改动时，同时读取 `git diff`、`git diff --staged` 与 `git status --short`。对未被忽略的未跟踪文件，使用 `git ls-files --others --exclude-standard` 固定清单，并把当前完整文件内容作为该 diff 范围的补充 snapshot 纳入评审；二进制或无法读取的文件必须说明原因，不得静默遗漏。用户同时指定路径时，三类输入都使用相同 pathspec 限制。
- 用户要求评审当前分支但未指定基点时，先检查当前分支、上游分支和默认分支；能够明确确定基点时使用 merge-base，不能明确确定时使用提问工具确认。
- 用户同时指定 Git 范围与文件或目录时，使用 pathspec 将 diff 限制到这些路径，不额外评审范围外文件。

分支范围默认使用 `git diff <fixed-point>...HEAD`，并记录 `git log <fixed-point>..HEAD --oneline`。引用无效或 diff 为空时立即停止并报告，不启动后续评审。

用户只指定文件或目录、要求评审当前实现且没有指定 commit、branch、PR、工作区变更或其他 diff 范围时，使用 **snapshot 模式**：

1. 将每个目标解析为仓库内真实存在的文件或目录；路径不存在、逃逸仓库或无法区分同名目标时停止并报告，不猜测。
2. 显式文件直接加入列表；目录优先使用 `rg --files --hidden -g '!.git/**'` 枚举受仓库忽略规则约束的文件并稳定排序，宿主没有 `rg` 时使用等价只读方式。二进制、生成物或无法读取的文件只可在说明原因后跳过，不得静默遗漏。
3. 记录当前 `HEAD`、目标路径、稳定文件列表和这些路径的 `git status --short`，审阅列表中当前工作区文件的完整内容。即使其中存在未提交改动，也不得静默缩小为 diff；只有用户明确要求“只看变更”时才切回 diff 模式。
4. 目录较大时按稳定文件列表分批，但所有批次仍属于同一次评审，必须覆盖完整列表后才能完成。

snapshot 文件列表为空时立即停止并报告。只要存在用户指定或能够按上述规则确定的 diff 范围，就保持 diff 模式；snapshot 仅用于没有该范围的文件或目录评审。

### 2. 定位需求来源

按以下顺序查找本次变更的需求依据：

1. 用户明确指定的 PRD、任务卡、Issue、PR 或当前对话目标；
2. commit 消息或变更文件中引用的任务卡；
3. 任务卡 `Parent` 指向的 `PRD.md`；
4. 与当前需求目录、分支名称或变更主题明确对应的本地 PRD/任务卡。

读取真实存在的完整内容，不根据文件名猜测需求。如果仍无需求来源，继续 Standards 评审，并在最终结果中把 Spec 标为“无可用需求依据”。

### 3. 加载项目规范

读取与评审范围相关的规范来源：

- 当前范围生效的 `AGENTS.md`、`CLAUDE.md` 或等效 Agent 指令；
- 当前任务已经由 `project-knowledge load` 返回的 CONTEXT 与 RULE，不自行定位或重复读取领域文档；
- 仓库内真实存在的编码规范、测试约定和模块约束；
- [standards-baseline.md](./standards-baseline.md) 中的通用评审基线。

项目明确记录的规则优先于通用基线。工具已经能够确定性检查的问题交给工具，不重复制造人工风格意见。

按调用来源决定是否加载 `codebase-design`：

- **用户直接发起评审**：默认读取 `codebase-design`，把模块职责、接口深度、依赖接缝、adapter、局部性和测试面纳入 Standards。即使用户没有另外强调“架构”或“重构”，也要主动检查当前范围内有具体证据的浅模块、复杂度泄漏、过宽接口、无真实变化的接缝和测试越过接口等问题。
- **由 `impl` 或其他流程作为交付检查调用**：仅当 diff 确实改变上述模块形状，或调用方目标明确包含架构评审时读取，避免普通实现产生范围外重构 finding。

无论哪种来源，都只报告当前评审范围中有代码、需求或项目规则证据的真实风险；不得要求替换项目已有术语，不得把偏好的架构风格写成缺陷，也不得提出超出本次范围的重构。

### 4. 并行执行两个评审维度

宿主支持子 Agent 时，必须并行安排两个只读子 Agent：

- **Standards Agent**：接收固定范围描述——diff 模式传入命令与 commit 列表，工作区 diff 还要传入未跟踪文件的稳定清单与完整内容；snapshot 模式传入 `HEAD`、路径、稳定文件列表和工作区状态——以及项目规范来源、完整通用基线和按调用来源确定的 `codebase-design` 判断准则。逐文件或代码块报告：(a) 违反的每一条项目规范，并引用规范文件与具体规则；(b) 命中的通用风险信号，并命名信号、引用对应 diff 或 snapshot 文件行；(c) 用户直接发起评审时，独立完成模块形状检查并报告有具体维护或测试影响的重构机会。明确区分项目规范的硬性违反与判断性提示；项目规范覆盖通用基线，跳过工具已经检查的事项。报告控制在 400 字以内。
- **Spec Agent**：接收相同固定范围和完整需求来源。报告：(a) 缺失或只完成一部分的需求；(b) 需求未要求的 scope creep；(c) 看似已实现但实现错误的需求。每条 finding 必须引用对应需求依据。报告控制在 400 字以内。

两个子 Agent 不得修改文件，也不得读取对方的中间结论。宿主不支持子 Agent 时，按相同输入顺序执行两个独立检查，并保持证据与结论分栏，不混写推理。

如果没有需求来源，跳过 Spec Agent。diff 模式没有 diff，或 snapshot 模式没有有效文件时，两个维度都不执行；合法 snapshot 不得因为没有 diff 而跳过 Standards。

### 5. 强制执行已加载 RULE 终检

聚合前，主 Agent 必须亲自重新校验本次 `load` 返回的全部 RULE，不能用 Standards Agent 的结论代替：

1. 确认 Hook 提供的选择范围覆盖本次评审；若评审范围扩大，按当前完整范围重新执行一次 `load`。
2. 逐条对照所有已加载规则与完整 diff 或 snapshot 文件内容，在内部检查表中标记为“符合”“不适用”或“违反”，并保留对应文件、行号或 diff 证据。
3. Standards Agent 漏报的违反必须补入 Standards；判断不清时标为终检未完成并说明缺失信息，不得宣称 Standards 通过。

最终报告必须列出本次覆盖的 RULE 文件，并明确终检是“通过”“存在上述违反”还是“未完成”。无需输出所有“符合”或“不适用”的中间检查项。

### 6. 聚合结果

按以下结构输出：

```markdown
评审范围：<diff：命令、基点与路径过滤；或 snapshot：HEAD、目标路径、文件数与工作区状态摘要>

## Standards

- [P1] <问题标题> — `<文件:行>`
  - 证据：<违反的项目规则或命中的基线>
  - 影响：<为什么会造成真实风险>
  - 建议：<最小修复方向>

RULES 终检：已覆盖 <RULES 文件列表>；<通过 / 存在上述违反 / 未完成及原因>

## Spec

- [P1] <问题标题> — `<文件:行>`
  - 需求依据：<PRD/任务卡中的对应条目>
  - 偏差：<遗漏、错误、scope creep 或验收缺口>
  - 建议：<最小修复方向>
```

严重级别使用 `P0` 到 `P3`：`P0` 阻断交付或造成重大事故，`P1` 高概率导致错误行为，`P2` 局部缺陷或明显维护风险，`P3` 低风险改进。没有发现时明确写“未发现问题”，不要为了填充报告制造意见。

允许轻度清理两份报告的表述，但不得跨维度合并或重排 finding。严重级别只在各自维度内比较，不选出跨维度的单一“最严重问题”。最后用一行分别汇总 Standards 与 Spec 的 finding 数量及各自最严重的问题；没有 finding 时标明无。

## 完成标准

- 范围模式明确；diff 的命令与基点可复现，工作区 diff 中未跟踪文件已显式纳入或说明无法读取的原因；或 snapshot 的 `HEAD`、目标路径、稳定文件列表和工作区状态已记录；
- Standards 与 Spec 使用各自真实来源，独立完成；
- 每个评审文件都已映射到生效的 RULES，且每条规则都得到“符合”“不适用”或“违反”的终检结论；
- 每条问题都包含紧凑文件位置、证据、影响和最小修复方向；
- 聚合结果没有跨维度合并或重排，并分别汇总两个维度；
- 不把推测写成缺陷，不报告工具已经覆盖的纯格式问题；
- 全程保持只读，没有修改工作区、提交或远端状态。
