# Code Review

对固定代码范围执行一次只读评审：

- **Standards**：逐条检查项目全部 RULE 与工程规范，并判断改动是否选择了最小正确实现。
- **Spec**：检查实现是否符合 PRD、任务卡等已确认需求。

调用方或用户指定 `--std` / `--spec` 时，视为维度锁：只跑被锁定的维度。未锁维度时，由本 Skill 判断每条依据的适用性并归入 Standards 或 Spec，只启用有依据的维度。两个维度只共享固定代码范围，不共享依据或 finding。本 Skill 不修改代码、提交或远端状态。

## 1. 加载项目上下文

按项目知识协议使用相关 CONTEXT。启用 Standards 时加载项目提供的完整 RULE 集合；已有知识只覆盖部分 RULE 时补全，范围扩大时重新确认。知识不可用时继续并如实说明。

全部项目 RULE，以及约束代码结构、写法、测试或工程协作的 Agent 指令归入 Standards；不因 RULE 涉及系统行为、状态、数据、校验、权限或业务流程而转入 Spec。PRD、API 清单、任务卡、Issue 和当前对话中的已确认需求归入 Spec。历史或被当前明确要求取代的材料不作为评审依据。

## 2. 固定评审范围

优先使用调用方或用户指定的 commit、branch、tag、range、PR 或路径，并记录实际 diff 命令和 commit 列表。分支使用 `git diff <fixed-point>...HEAD`。

调用方指定的 commit、range 或 pathspec 与用户指定同等优先。`impl` 传入单笔提交时，范围就是该 SHA，不使用分支 merge-base。

用户未明确固定点时：

- PR 编号或 URL：解析真实 base、head 和 patch；
- 当前分支：使用可确认的上游或默认分支 merge-base，无法确认时提问；
- 未提交改动：覆盖未暂存、已暂存和未跟踪文件；
- 文件或目录当前实现：完整读取 [SNAPSHOT.md](./SNAPSHOT.md) 固定文件列表和工作区状态。

用户指定路径时用同一 pathspec 限制范围。引用无效、diff 为空或 snapshot 无有效文件时停止。

## 3. Standards 评审

读取范围内生效的 `AGENTS.md`、`CLAUDE.md`、项目完整 RULE 集合，以及用户明确指定的其他工程规范。PRD、任务卡等需求不进入 Standards。记录每个来源的路径、准确标题和具体条款；没有明确来源的观点不是评审依据。

Standards 维度由一个 Standards 子 Agent 单次完成。主 Agent 先固定范围并准备完整工程规范，再把 diff、必要上下文和规范一次性交给它。

### RULE 逐条核对

逐条读取并核对项目完整 RULE 集合，不按关键词、文件名或主观相关性预筛。每个 RULE 的原始标题都必须出现在最终表中，并判定为：

- `违反`：固定范围内有代码直接违反具体条款；
- `未违反`：已核对固定范围，没有发现违反；
- `不适用`：条款约束的技术、模块或场景未出现在固定范围，原因必须可复核；
- `无法判断`：缺少判断该条款所必需的代码或上下文，写清缺口，不把它包装成问题。

`违反`必须同时给出 RULE 的路径与具体条款、代码位置、违反原因和大致修改方向。不能指出具体条款或代码证据时，不得判为违反。

### 必要性审查

完整读取 [MIN-IMPL.md](../codebase-design/MIN-IMPL.md)。对固定范围内每个 changed hunk 及其完整 enclosing symbol 逐段回答：

1. 这段代码具体做什么，服务哪个已确认行为或真实调用者？
2. 它必须存在吗；删除后，已确认行为是否仍然成立？
3. 删除、复用现有代码、标准库、平台原生能力或已安装依赖，能否让实现更简单？
4. 删除或替换后，文件、类型、分支、状态和概念的净数量是减少还是增加？

如果删除后行为仍正确且实现更简单，这段代码违反 `MIN-IMPL.md`，应当删除。如果必须用更复杂的实现才能维持正确行为，则保留。只有能够说明真实调用路径、删除前后行为和净复杂度变化时，才能报告必要性问题；猜测未来扩展、泛泛代码味道、个人偏好和“也许更优雅”都不构成问题来源。

修复缺陷时检查待修改位置的全部调用者；共同根因能够在真实所有者修复时，把散落在调用者的补丁作为 `MIN-IMPL.md` 违反报告。`codebase-design` 只在已证明确有必要调整模块形状时读取。

Standards 子 Agent 返回最终表所需的全部 RULE 行和必要性违反。主 Agent 逐行复核来源、代码位置、影响与修改方向；任何问题缺少明确来源或具体证据时删除该行。

## 4. Spec 评审

按以下顺序读取本次需求依据：

1. 用户指定的 PRD、API 清单、任务卡、Issue、PR 或当前对话目标；
2. commit 或变更明确引用的需求来源；
3. 与变更主题明确对应的本地需求文档。

CONTEXT 可帮助理解项目术语，但不代替需求来源。项目 RULE、当前代码和工程惯例不转成 Spec 需求。没有可用需求依据时跳过 Spec，并如实说明。

Spec 只报告需求遗漏、错误行为和需求之外的 scope creep；命名、重复、架构和测试写法不进入 Spec。每条适用的已确认需求都在本轮内部判定为符合、不适用或违反。

调用方给出的需求材料必须纳入 Spec 分类，不得静默丢弃；候选 `ruleId` 统一进入 Standards 表。需求判定不适用只允许四类可复核理由：历史、场景不匹配、被本次明确要求取代、不在本单元业务结果内；缺这类理由时保持适用。调用方声明本单元业务结果后，未纳入该结果的其余需求判不适用，不报遗漏。

需求材料在本提交中已被用户确认修正时，以修正后的文本为 Spec 依据。实现方私下的解释、注释或偏差记录不构成依据。Implementation Decisions 中来源为用户确认的授权例外，对应条款判定为不适用，并在覆盖状态中说明。

## 5. 执行与终检

只启用 Standards 时创建一个 Standards 子 Agent，只启用 Spec 时创建一个 Spec 子 Agent；两个维度同时启用时并行创建两者。每个子 Agent 只接收自己的完整依据和固定范围，一次返回工程规范或需求覆盖状态及候选 finding。

主 Agent 核实候选引用的代码、影响和本维度依据，删除不成立、越界、串用依据或没有明确来源的候选，并确认项目完整 RULE 集合的每个标题都有一行。缺少覆盖时只补核遗漏规则，不重复完整评审。

保留问题前必须同时确认：位置准确、影响具体、依据属于本维度、建议是最小正确方向。Spec finding 的严重程度由终检结果确定：`P0` 阻断交付或造成重大事故，`P1` 高概率错误行为，`P2` 局部缺陷或明确维护风险，`P3` 低风险但有具体收益。

## 6. 输出

`--std` 只输出评审范围和一张 Standards 表。未锁维度或 `--spec` 时，只为启用的维度追加对应内容。

Standards 表必须包含项目完整 RULE 集合的全部原始标题。其他工程规范只有违反时才增加一行，并使用来源文件中的准确标题；必要性问题使用固定来源标题 `最小实现阶梯 / MIN-IMPL.md`。同一来源存在多个违反时可有多行。没有明确来源的问题不输出。

```markdown
评审范围：<固定点、diff 命令和路径>

## Standards

| Rule 标题 | 判定 | 源头 | 代码证据 | 原因 | 大致修改方向 |
|---|---|---|---|---|---|
| `<原始标题>` | `违反 / 未违反 / 不适用 / 无法判断` | `<来源路径:行，具体条款>` | `<代码路径:行；无则 —>` | `<判定理由>` | `<违反时写最小方向；否则 —>` |
| 最小实现阶梯 / MIN-IMPL.md | `违反` | `codebase-design/MIN-IMPL.md:<行，具体条款>` | `<代码路径:行>` | `<用途、真实调用者、删除前后行为及净复杂度变化>` | `<删除或更简单的替代>` |

## Spec
- [SPEC-001] [P1] <问题> — `<文件:行>`
  - 需求依据：<需求来源及具体要求>
  - 偏差：<遗漏、错误或 scope creep>
  - 最小修复：<方向>

需求：已覆盖 <来源列表>；<通过 / 存在上述违反 / 未完成>
```

表后只写一行结论：`Standards：通过 / 存在 N 条违反 / 有 N 条无法判断`。不再另列 Standards finding。没有违反时也必须保留完整 RULE 表，不制造改进意见，不估算净减少行数。
