# Atomic Commit

核心目标是把一个完整交付单元提交在一起，并确保它可以整笔直接回滚。提交边界由交付完整性和回滚边界决定，不追求最小、最细。

## 原子性标准

- **完整交付单元**：一次交付所需的实现、测试、文档、配置、迁移和生成文件可以放在同一 commit。该 commit 在其依赖基线之上能够完整成立、整体验证，不依赖剩余未提交改动。
- **可直接回滚**：可以通过整笔回滚该 commit 撤销这次交付，无需挑选 hunk、同时回滚无关提交或手工拼接恢复状态；回滚后不会留下明显残缺状态。
- **边界优先于粒度**：不以文件数、改动量、技术层次、约定式提交类型或“一个可观察结果”追求最小、最细。只要内容共同构成一个完整交付单元并共享回滚边界，就可以作为一个 commit。
- **按交付与回滚关系拆分**：只有当改动不属于同一交付单元，或无法安全地一起验证、交付和回滚时才拆分。

## 流程

使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。

1. 优先根据当前会话理解变更目的和范围。查看 `git status`，并只读取划分提交边界和生成消息所需的相关 diff；不得为重新理解已知改动而扩大调查。
2. 在暂存前确认提交边界。调用方已给出交付单元时先验证其完整性和直接回滚能力；没有时按交付内容、验收方式和回滚边界划分。不要为了缩小提交而继续拆分一个已经完整且可直接回滚的交付单元。
3. 逐个交付单元执行：
   - 只暂存该单元的路径或 hunk；
   - 检查 staged diff，确认内容完整、没有无关改动，也不依赖剩余未提交改动；
   - 沿用当前会话已经完成的验证并如实保留验证边界；
   - 为 staged diff 生成消息并完成本地提交，再处理下一个单元。
4. 调用方给出的交付单元与 diff 不一致时，写入前返回边界冲突。改动归属不清，或用户要求的提交方式会破坏交付完整性或直接回滚能力时，提问确认。
5. 提交消息涉及业务术语时，使用 CONTEXT 中的统一术语，并使用以下格式：

   ```text
   <type>[(scope)]: <summary>

   [body]

   [footer]
   ```

6. 选择最贴近变更目的的类型：
   - `feat` 新功能；`fix` 缺陷修复；`refactor` 重构；`perf` 性能优化；
   - `docs` 文档；`test` 测试；`build` 构建或依赖；`ci` 持续集成；
   - `style` 不影响逻辑的格式调整；`chore` 其他维护；`revert` 回退提交。
7. `scope` 仅在能稳定指向模块、组件或业务领域时使用；无法准确归类时省略。
8. `summary` 使用祈使语气，直接描述变更带来的结果；不加句号，标题不超过 72 个字符。沿用用户和代码中已确定的术语，不臆造命名。
9. 只有标题无法说清变更内容或原因时才添加 `body`；说明「改了什么、为什么改」，不复述代码实现细节。
10. 破坏性变更在类型后加 `!`，并在 `footer` 中写明 `BREAKING CHANGE: <影响>`。关联信息按需使用 `Refs: #123`。

## 执行边界

- 只暂存当前会话相关的改动。如果已暂存内容的归属不清，在写入前提问确认。
- 不得自动 push。

## 示例

```text
fix(订单): 处理空订单号时不再崩溃
```

```text
feat(api)!: 使用信封格式包装审批响应

统一响应元数据的承载方式。

BREAKING CHANGE: 客户端必须从 data 字段读取原响应内容
```
