# Atomic Commit

核心目标是先划定正确的提交边界，再用准确、简洁、可追溯的消息说明每个逻辑变更。每个 commit 必须在其依赖基线之上可独立理解、验证和回滚。

## 原子性标准

- **单一目的**：一个 commit 只交付一个可观察结果，边界由验收和回滚关系判断，不按文件类型、技术层次或约定式提交类型机械拆分。
- **完整闭环**：实现及其必要的测试、文档、配置、迁移和生成文件放在同一 commit；不得把一个逻辑变更按文件类型机械拆开，也不得依赖未提交改动才能成立。
- **可独立审阅与回滚**：仅查看该 commit 就能判断目的和影响；仅回滚该 commit 不会连带撤销无关行为，也不会留下明显残缺状态。
- **边界优先于大小**：原子提交不等于最小行数或单文件提交。只要围绕同一目的且缺一不可，可以包含多个文件；若包含多个可分离目的，就必须拆分。

## 流程

1. 优先根据当前会话理解变更目的和范围。查看 `git status`，并只读取划分提交边界和生成消息所需的相关 diff；不得为重新理解已知改动而扩大调查。
2. 在暂存前确认提交边界。调用方已给出实现单元时先验证该边界；没有时按目的、验收方式和回滚边界划分逻辑单元。多个独立目的默认拆分并按依赖顺序提交。
3. 逐个逻辑单元执行：
   - 只暂存该单元的路径或 hunk；
   - 检查 staged diff，确认内容完整、没有无关改动，也不依赖剩余未提交改动；
   - 沿用当前会话已经完成的验证并如实保留验证边界；
   - 为 staged diff 生成消息并完成本地提交，再处理下一个单元。
4. 调用方给出的实现单元与 diff 不一致时，写入前返回边界冲突。改动互相缠绕、归属不清或用户要求的提交数量违反原子边界时，提问确认。
5. 提交消息涉及业务术语时，优先使用当前会话已知的统一术语，并使用以下格式：

   ```text
   <type>[(scope)]: <summary>

   [body]

   [footer]
   ```

6. 选择最贴近变更目的的类型：
   - `feat` 新功能；`fix` 缺陷修复；`refactor` 重构；`perf` 性能优化；
   - `docs` 文档；`test` 测试；`build` 构建或依赖；`ci` 持续集成；
   - `style` 不影响逻辑的格式调整；`chore` 其他维护；`revert` 回退提交。
7. `scope` 仅在能稳定指向模块、组件或业务领域时使用；无法准确归类时省略。
8. `summary` 使用祈使语气，直接描述变更带来的结果；不加句号，标题不超过 72 个字符。沿用用户和代码中已确定的术语，不臆造命名。
9. 只有标题无法说清变更内容或原因时才添加 `body`；说明「改了什么、为什么改」，不复述代码实现细节。
10. 破坏性变更在类型后加 `!`，并在 `footer` 中写明 `BREAKING CHANGE: <影响>`。关联信息按需使用 `Refs: #123`。

## 执行边界

- 用户只要求「写提交消息」或「审查消息」时，只输出结果，不执行 Git 写入；若范围包含多个逻辑单元，分别给出消息及其对应边界。
- 用户要求「提交」时，只暂存当前会话相关的改动。如果已暂存内容的归属不清，在写入前提问确认。
- 不得自动 push。

## 示例

```text
fix(订单): 处理空订单号时不再崩溃
```

```text
feat(api)!: 使用信封格式包装审批响应

统一响应元数据的承载方式。

BREAKING CHANGE: 客户端必须从 data 字段读取原响应内容
```
