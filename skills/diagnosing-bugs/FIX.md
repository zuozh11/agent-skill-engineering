# 修复与回归

仅当 `diagnosing-bugs` 已完成阶段 1–4，且用户明确要求修复时完整读取并使用本文件。

## 阶段 5 — 修复 + 回归测试

在修复**之前**编写回归测试——但前提是存在**正确的接缝**：测试能在调用点处执行**真实的 bug 模式**。接缝太浅（需要多调用者才能触发，却只有单调用者测试）只会给出虚假信心。

**如果不存在正确的接缝，这本身就是发现。** 记录下来：代码库架构正在阻止 bug 被锁定。将此标记给下一阶段。

如果存在正确的接缝：

1. 将最小化的复现转化为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. **校验修复符合已加载 RULE。** 绿灯但违反本次 `load` 返回的规则仍视为未完成——回去重做。确需偏离某条规则时，显式标出冲突、说明理由，交用户裁决。
6. 对原始（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后分析

宣布完成前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或接缝缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）；无标签的日志留存，有标签的日志删除
- [ ] 一次性原型已删除（或移至明确标记的调试位置）
- [ ] 最终正确的假设已在 commit / PR 消息中陈述——以便下一个调试者学习

**然后问：什么能预防这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、纠缠的调用者、隐藏的耦合），在修复完成**之后**记录具体的后续改进建议——你现在比开始时掌握了更多信息。
