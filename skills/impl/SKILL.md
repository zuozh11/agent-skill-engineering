# Impl

根据需求自行分解提交单元，逐个做最小实现，然后调用 `atomic-commit` 提交。

`-w` 使用隔离 worktree，`-a` 使用子 Agent 或 workflow 编排，`--review` 或 `-r` 在提交前执行一轮 Standards 评审和修复；三个选项独立且可组合。用户明确要求 worktree、子 Agent / workflow 或提交前评审时，分别按对应选项执行。使用 `-w` 或 `-a` 时，实施前完整读取 [ISOLATION.md](./ISOLATION.md)。

## 流程

### 1. 加载项目上下文

按项目知识协议执行。过目 scope 返回的全部 sceneId 与 ruleName，加载与本轮实现相关的场景或原子 RULE。会话已有知识仅在覆盖本轮实现时复用，不够则补 load。知识不可用时继续并如实说明，且不得声称已遵守。

### 2. 分解提交单元

提交单元以可独立说明的业务意义为边界：完成后，用户、角色或系统获得一项完整能力，或者产生一个可观察的业务结果。从任务卡、PRD、API 清单或当前对话中识别这些结果；共同完成同一结果所需的代码、测试、配置、迁移和文档放在同一单元，不按文件、技术层、接口数量或改动类型拆分。

只有形成不同且各自完整的业务结果时才拆分。每个提交单元还需满足 `atomic-commit` 的交付完整性与直接回滚标准。

### 3. 实施并提交

逐个提交单元执行：

1. 查看现有代码，将需求映射到实际结构。映射后尚未覆盖的相关场景或原子 RULE 补 load。
2. 改动涉及模块职责、接口表面积、接缝、adapter、测试面或深浅程度时，读取 `codebase-design`，根据需求、真实代码和项目规则确定必要设计；存在影响显著的可行方案分歧时，调用 `ask-me` 与用户确认。
3. 做范围内的最小修改，优先复用现有能力。不添加需求与规则之外的兜底或防御性设计。
4. 使用 `--review` 或 `-r` 时，以本提交单元的当前改动为固定范围调用一次 `code-review --std`。只修复其最终报告中确认存在的问题，不重复评审。
5. 提交前核对每条已加载 RULE：就本单元改动判定符合或不适用，违反先改到符合。核对在实现过程内完成，通过后调用 `atomic-commit`，以当前提交单元为交付单元完成一个本地提交。

代码事实证明方案不可行，或需要扩展范围、改变已收口方案时停止并报告。
