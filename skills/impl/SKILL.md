# Impl

根据任务卡或当前对话实现代码变更，两种输入方式地位相同。

**原子提交是本 Skill 最核心的原则：每个 commit 只表达一个可独立理解和回滚的变更。**

## 调用参数

- `-w`：强制使用隔离 worktree 模式，不再执行自动分流。`impl -w`、`/impl -w`、`$impl -w` 以及在其后继续提供任务描述或 task 文件路径，均视为用户已明确指定隔离模式。
- 参数只覆盖执行方式，不改变实现范围、任务依赖、原子提交和安全规则。

## 流程

开始前检查并记录主工作区中已有的已暂存、未暂存和未跟踪改动。工作区不 clean 本身不阻塞实现；已有改动视为用户所有，不得自动 stash、覆盖、暂存或提交。仅当已有改动与本次范围重叠，且无法可靠地分离或归属本次改动时，才暂停并请用户处理。

### 1. 确定实现单元

从用户提供的输入中确定本次要完成的独立实现单元：

- **任务卡输入**：读取指定的 task 文件，理解目标、现状、方案和验收条件，并按 `ready-for-agent → completed → archived` 维护状态。
- **对话输入**：从当前对话提取目标、范围、已确定的方案和验收方式；上下文足够时直接实现，不要求先生成任务卡。

如果一次包含多个可独立完成的改动，先划分实现单元，后续分别实现和提交。只有缺少的信息会真正阻塞实现时，才调用 `grill-with-docs` 与用户对齐。

以任务卡为输入时，先检查执行资格：

- 只有 `Status: ready-for-agent` 的任务可以进入调度；`completed` 任务不重复实现
- 存在 `Blocked by` 时，读取其中引用的任务卡；只有全部依赖均已完成，当前任务才解锁
- 依赖引用不存在、状态异常或形成循环时，停止对应任务并报告
- 一次输入多个任务时，只调度当前已解锁的任务，其余任务等待依赖集成

#### 多任务卡上下文隔离

一次输入多张任务卡时，每张已解锁任务卡必须在独立的全新执行上下文中实施。单张任务卡或对话输入继续使用当前上下文，不为形式隔离另建执行上下文。

- 新执行上下文只接收当前任务卡、相关 `CONTEXT.md`、全部项目 RULES、当前已集成的代码，以及必要的依赖任务状态和提交结果；其他任务实现过程中的临时判断不得带入，跨任务决定必须已经写入任务卡、领域文档或代码
- 存在依赖时，前置任务提交并集成后，后续任务才从最新目标分支启动全新执行上下文
- 上下文隔离不决定使用当前工作区还是 worktree，也不决定执行者或串并行方式；继续按后续步骤根据依赖、共享写集和隔离收益选择
- 独立任务只有在分别使用独立 worktree、Git 索引和临时分支时才可并行；否则各执行上下文按顺序实施
- 当前宿主无法创建全新执行上下文时，本次只执行一张任务卡并报告其余任务，不得在同一上下文中连续实施多张任务卡

### 2. 评估并确定执行方式

用户通过 `-w` 或自然语言明确指定隔离模式时，直接使用隔离 worktree 模式；用户明确指定当前工作区时，直接在当前工作区实现。未指定时，根据已确定的实现单元评估并直接执行推荐方式：

- **推荐当前工作区实现**：实现范围集中，已有改动与本次范围不重叠，或创建和集成 worktree 的开销明显大于隔离收益。
- **推荐隔离 worktree 实现**：用户已有改动需要保护；实现范围较广或风险较高，需要独立分支和提交边界；或多个已解锁实现单元需要彼此隔离。

在开始实现前简要说明选定的方式和一项关键依据，不请求用户确认。仅当已有改动的归属、实现范围或隔离收益无法从任务卡和代码事实中确定，两种方式的利弊仍接近时，才调用当前宿主的提问工具。执行方式确定后，除非用户重新指示，不得自动切换或降级。

### 3. 加载领域知识与编码约束

使用以下领域资源：

- **领域文档**：按 `docs/agents/domain.md` 定位并使用相关 `CONTEXT.md`；所有项目规则均必须遵守。相关 `CONTEXT.md` 不存在则静默继续。

### 4. 按选定方式实现

#### 当前工作区实现

- 在当前工作区内实现、检查和提交，不创建 worktree 或临时分支
- 多个实现单元按依赖顺序串行处理；无依赖时按任务卡编号或输入顺序处理
- 每完成一个实现单元，先暂存其范围内的改动并检查 staged diff，再进入最终 RULES 自检门；通过后交付原子 commit，再继续下一个

#### 隔离 worktree 实现

- 每个需要独立交付的实现单元使用独立 worktree 和临时分支
- 存在依赖的实现单元必须在依赖集成后，从最新目标分支创建 worktree
- 多个执行过程不得共享同一 worktree、Git 索引或临时分支
- 发现实现单元存在共享写集或明显冲突时，按依赖串行处理，不修改任务卡
- 无法安全创建 worktree 时，说明原因并暂停，由用户决定是否改用当前工作区实现

#### 共同实现与提交规则

- 严格遵守所有项目 RULES；存在 task 文件时，同时重点关注其中列出的 RULES
- 根据任务卡或对话确定的目标查看现有代码，将已确定的方案映射到实际代码结构，并识别必要的修改点
- 不重新选择任务卡或对话中已经收口的主要方案；若代码事实证明方案不可行或互相矛盾，停止实现并明确报告，而不是自行改换方案
- 遵守 `CLAUDE.md` / `AGENTS.md` 中的编码指南和规则
- 匹配实现范围内相关的 Skill
- 不添加实现范围之外的功能、重构或抽象
- 每次提交前只暂存当前实现单元的改动，并检查 staged diff；已有改动不得进入本次 commit
- 每个 worktree 只处理对应实现单元的范围；暂存并检查 staged diff 后，必须通过最终 RULES 自检门才能交付原子 commit
- 一个任务默认形成一个 commit；确有多个可独立理解和回滚的变更时，可以交付有序的 commit 列表
- 隔离模式下必须记录全部 SHA 及其目的，不得交付 WIP、fixup 或其他过程性提交
- 发现实现超出任务范围、改变既定方案或引入新的任务依赖时，停止并重新拆分
- 隔离 worktree 中不修改任务卡状态

### 5. 通过最终 RULES 自检门

每个实现单元完成实现、测试、验收和 staged diff 检查后，在提交、集成、更新任务状态或宣布完成前，必须对照全部项目 RULES 逐条检查本次分析、实现、测试、验收和待提交改动，不得只检查 task 文件「相关 RULES」中列出的规则。

- 任一 RULES 未满足，必须先修正实现、补充验证，并重新执行全部自检；违反任何 RULES 的实现均视为未完成。
- 任一 RULES 是否满足仍无法确认，或 RULES 之间、RULES 与任务方案之间存在冲突时，不得提交、集成、更新任务状态或宣布完成；先查证，无法从仓库确认时使用 `提问工具` 与用户对齐。
- 只有确认全部 RULES 均已遵守，才允许提交当前实现单元，随后进入集成与状态流转。

### 6. 集成与状态流转

当前工作区模式在每个实现单元的原子 commit 完成后直接进入状态流转，不执行 cherry-pick、worktree 或临时分支操作。

隔离模式下，按任务卡编号依次集成；无任务卡时按实现单元顺序集成。

- 按提交顺序完整 cherry-pick 一个实现单元的全部 commits；全部成功后，该实现单元才视为集成完成
- cherry-pick 冲突时中止本次集成并保留 worktree，在对应 worktree 中基于最新目标分支处理；冲突来自主工作区相关未提交改动时，暂停并请求用户处理
- 单个任务失败不影响无依赖的成功任务；失败任务只阻塞依赖它的后续任务
- 集成成功后移除 worktree 和临时分支
- 未成功集成的 worktree 和临时分支必须保留，并报告路径、分支和失败原因

两种模式共同遵守：

- 实现单元成功提交或集成后，将对应任务改为 `completed`
- 同一 `tasks/` 目录下全部任务均为 `completed` 时，统一改为 `archived`

## 硬性规则

- **不扩展 scope**：只做任务卡或对话确定的改动，发现相邻问题只提醒不修
- **不过度抽象**：匹配现有代码风格，不引入任务未要求的设计模式
- **积极复用**：优先复用现有能力、组件和同类实现，不重复实现已有逻辑，也不为复用扩大实现范围
- **不猜 API**：不确定的框架 API 先 grep 现有代码中的用法，再查 references
