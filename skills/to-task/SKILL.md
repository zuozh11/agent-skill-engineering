# To Task

将需求拆解为可独立落地、原子提交且具有明确验收结果的任务卡。任务卡先用业务语言呈现可评审的功能口径，再单独给出已确认事实和实现方案，使评审者能判断功能是否正确，未参与讨论的实现者也能直接动手。

## 流程

### 1. 收口需求与实施边界

读取 PRD、task、当前对话、截图或其他真实需求来源，提取每个可交付功能要做的内容、会改变实现的规则和可观察的验收结果。需求背景、业务价值和纯介绍性内容留在需求源中。

使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。

用户明确指定交付单元时按指定范围拆分。用户未指定时，以当前仓库作为交付单元并遵守其可实施边界：后端仓库只产出后端任务卡，前端仓库只产出前端任务卡；只有无法判断当前仓库属于哪个交付单元时，才提问确认后继续。涉及多个交付单元时仍按端到端行为拆分，不按交付单元横向拆分。

无法从需求、代码和领域事实确认主要方案或业务口径时，调用 `grill-with-docs` 完成查证和共识确认；收口后再继续。

### 2. 调研并收口方案

核对现有实现与项目惯例，形成两类结果：

- **已确认事实**：从代码、配置、数据或项目规则中查证的现有流程、能力、缺口、代码入口、数据库现状和约束
- **实现方案**：主要实现位置与处理路径，以及必须复用的能力、数据或状态变化、接口契约、处理顺序和事务边界

当前调研涉及模块职责、接口表面积、依赖接缝、adapter、测试面或模块深浅时，读取 `codebase-design`。普通需求沿用或合理扩展现有模块形状；存在影响显著的可行方案分歧时，由 `grill-with-docs` 组织决策并等待用户确认。

只定位足以实施的核心接口、流程、模块、扩展点和必要类或方法，不穷举辅助修改点，也不提前编写实现代码。

### 3. 选择拆分策略

普通需求默认拆成 **vertical slice / tracer bullet**。每张任务卡交付一个切穿必要层次、可独立观察和验收、并能由实现者在单个全新上下文中完成的端到端行为，对应一个预期 commit。卡内内容具有共同验收与回滚边界；能独立验收或回滚的目的另拆任务，服务同一结果的必要重构、测试、文档、配置和迁移保留在本卡。仅在存在真实业务依赖或预计写集冲突时设置 `Blocked by`。

仅当共享字段改名、公共模型换型、基础接口迁移等机械性变化横跨大量调用方，任何 vertical slice 都无法独立保持系统可用时，完整读取并使用 [expand-contract.md](./expand-contract.md)。跨模块开发本身不属于宽范围重构。

### 4. 写入任务文件

#### 路径、命名与依赖

- 有 PRD 时，从 PRD 的父目录派生 `tasks/` 路径。
- 没有 PRD 时，沿用用户指定的已有需求目录；否则扫描 `docs/scratch/` 直属目录中匹配「开头连续数字 + 连字符」的前缀，取最大值加一，从 `01` 开始，至少两位零填充。历史无编号目录不迁移、不参与计数。创建前重新扫描；目标已存在则继续递增。
- 需求目录使用 `<NN>-<中文需求名称>`，任务文件使用 `NN-<中文任务名称>.md` 并按依赖顺序编号。中文名称使用 CONTEXT 中的统一术语和端到端目标，不改写成英文 slug 或拼音。
- `Blocked by` 只表达真实业务依赖或预计写集冲突；任务编号和实现习惯不构成依赖。存在依赖时写明准确任务文件名和串行原因：

```yaml
Blocked by:
  - task: 01-创建公共接口.md
    reason: 后续任务依赖该接口
```

按依赖顺序写入任务卡，blocker 在前。

#### 内容结构

任务卡按以下阅读顺序组织：

1. **本次做什么**：用可评审的业务语言描述端到端行为和处理顺序，不使用代码现状解释功能；仅当某个技术标识本身就是需求契约时才保留。
2. **功能规则（如有）**：只写会改变实现的约束。删掉某条后，如果实现者可能写出不同的分支、数据口径、状态变化、权限范围、事务边界或接口契约，该内容才是功能规则；没有真实规则时省略整个章节。
3. **验收标准**：使用「场景 / 操作 / 预期结果」对照表，覆盖主流程、影响实现的边界和失败场景。
4. **已确认事实**：在分隔线之后集中列出已查证的代码、数据库、配置和项目约束，不混入待实现方案。
5. **实现方案**：按主要实现位置分组，写清改动目标、复用点、处理顺序、数据变化、接口契约和事务边界。

会影响实现决策的排除项作为否定规则写入「功能规则」；其余范围介绍留在需求源中。不创建「为什么做」「本次不做什么」或「技术验证」章节。构建、运行和 diff 检查由 `impl` 根据项目规定执行。

流程使用有序列表，并列项使用无序列表，关键短语使用粗体，代码标识使用行内代码。功能规则默认使用有序列表和粗体主题；只在存在多列比较、映射或计数关系时使用表格。

#### 模板

```markdown
---
Status: ready-for-agent
Blocked by: []
---

# <中文任务标题>

## 需求来源

<有 PRD：[需求标题](../PRD.md)；无 PRD 时写一句话需求摘要或指向真实存在的需求来源>

## 本次做什么

<用可评审的业务语言写清本任务交付的端到端行为；有处理顺序时使用有序列表>

## 功能规则

1. **<规则主题>**：<会影响分支、数据口径、状态、权限、事务或接口契约的规则>

<!-- 只有存在真实功能规则时才保留本章节；没有时连同标题一起删除。 -->

## 验收标准

| 场景 | 操作 | 预期结果 |
| --- | --- | --- |
| <主流程> | <用户操作或系统触发> | <可观察结果> |
| <边界或失败场景> | <用户操作或系统触发> | <可观察结果> |

---

## 已确认事实

- <从代码、数据库、配置或项目规则中已查证的现状>
- <实现需要复用的已有能力或必须考虑的约束>

## 实现方案

### <主要实现位置> — <改动目标>

<写清主要处理路径，以及必要的能力复用、数据或状态变化、接口契约、处理顺序和边界>
```

每张任务卡必须同时满足：

- **功能可评审**：评审者只阅读「本次做什么」「功能规则」（如有）和「验收标准」，无需先理解代码就能判断功能口径是否正确。
- **方案可实施**：未参与需求讨论的实现者阅读「已确认事实」和「实现方案」后，无需重新询问业务口径、调研主要代码入口或选择主要方案，即可开始实施。
- **粒度可执行**：方案只定位核心改动目标和约束，不穷举辅助文件、内部方法和代码行，不提前编写实现代码。

通过后交付。
