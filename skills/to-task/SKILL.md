# To Task

将需求拆解为可独立落地、原子提交并具有明确验收方式的任务卡，使未参与需求讨论的实现者拿到即可直接动手。普通需求使用 vertical slice；无法保持每个切片独立可用的宽范围机械改造使用 expand-contract。

任务卡必须收口业务口径、主要实现位置、方案、数据契约和验收方式，但不得提前编写实现代码，也不穷举可由实现过程自然确定的辅助文件、内部方法和代码行。

任务文件写入 `docs/scratch/<NN>-<中文需求名称>/tasks/`。

## 流程

### 1. 明确需求与领域边界

读取 PRD、task、当前对话、截图或其他真实需求来源，提取目标、业务口径和验收方向。

按 `docs/agents/domain.md` 定位并使用相关 `CONTEXT.md`，所有项目规则均必须遵守；相关领域文档不存在则静默继续。任务标题和方案使用 `CONTEXT.md` 中的统一术语。

无法从需求、代码和领域事实确认实施所需的主要方案或业务口径时，调用 `grill-with-docs` 完成查证、追问和共识确认。未收口不得继续拆解。

### 2. 调研并收口方案

核对现有实现与项目惯例，完成足以让实现者直接动手的调研和方案设计。每张任务卡必须明确：

- 当前流程、能力缺口和目标端到端行为；
- 主要实现位置与处理路径，以及必须复用的能力、数据或状态变化、接口契约、处理顺序和边界；
- 可独立执行的验收操作及可观察结果。

每次调研和收口方案时都读取 `codebase-design`，用其共享词汇与判断准则检查模块职责、接口表面积、依赖接缝、adapter、测试面和模块深浅。普通需求只确认方案沿用或合理扩展现有模块形状，不得为了使用本 Skill 强行制造重构；存在影响显著的可行方案分歧时，仍由 `grill-with-docs` 组织决策并等待用户确认。

只定位核心接口、流程、模块、扩展点以及必要的类或方法，不为制作任务卡穷举辅助修改点。

### 3. 选择拆分策略

#### 普通需求：vertical slice

将需求拆成 **tracer bullet** 任务。每张任务卡必须：

- 交付一个切穿必要层次、可独立观察和验证的端到端行为；
- 能由实现者在单个全新上下文中完成实现、验证和原子提交；超出时继续按端到端行为切薄，不得改为按技术层次横向拆分；
- 仅在存在真实业务依赖或预计写集冲突时使用 `Blocked by`，否则保持独立。

`Blocked by` 有依赖时必须包含准确的任务文件名和串行原因；任务编号和实现习惯不能作为依赖关系。

```yaml
Blocked by:
  - task: 01-创建公共接口.md
    reason: 后续任务依赖该接口
```

#### 宽范围重构：expand-contract

仅当共享字段改名、公共模型换型、基础接口迁移等机械性变化横跨大量调用方，任何单个 vertical slice 都无法独立保持系统可用时，使用 expand-contract。跨模块开发本身不属于宽范围重构。

1. **Expand**：引入新结构或接口，保留旧形式的兼容路径。
2. **Migrate**：按模块、包或影响面分批迁移；每批依赖 Expand，并明确迁移范围和验证方式。
3. **Contract**：全部 Migrate 完成后删除旧结构、兼容路径和过渡代码，并依赖全部 Migrate 任务。

Expand、每个 Migrate 批次和 Contract 都必须可独立落地，使系统保持可用，并通过任务范围内项目规定的构建、测试或验收。仅当单个迁移批次确实无法独立验证时，才在任务卡中明确共同集成点、串行原因和最终集成验证任务。

### 4. 写入任务文件

按依赖顺序（blocker 先写入）创建任务文件：

- 有 PRD 时，从 PRD 的父目录派生 `tasks/` 路径。
- 没有 PRD 时，沿用用户指定的已有需求目录；否则扫描 `docs/scratch/` 直属目录中以连续数字和连字符开头的目录，取最大编号加一，从 `01` 开始并至少两位零填充。历史无编号目录不迁移、不参与计数；创建前重新扫描，发生碰撞时继续递增。
- 需求目录使用 `<NN>-<中文需求名称>`，任务文件使用 `NN-<中文任务名称>.md` 并按依赖顺序编号。中文名称使用 `CONTEXT.md` 中的统一术语和端到端目标，不得改写成英文 slug 或拼音。

### 5. 通过最终 RULES 自检门

交付任务卡前，必须对照全部项目 RULES 逐条检查本次分析、方案设计、任务拆分、任务卡内容和验收方式，不得只检查任务卡「相关 RULES」中列出的规则。

- 任一 RULES 未满足，必须先修正任务卡并重新执行全部自检。
- 任一 RULES 是否满足仍无法确认，或 RULES 之间、RULES 与需求之间存在冲突时，不得交付任务卡；先查证，无法从仓库确认时调用 `grill-with-docs` 与用户对齐。
- 只有确认全部 RULES 均已遵守，才允许宣布 `to-task` 完成并交付任务卡。

## task 文件模板

```markdown
---
Status: ready-for-agent
Blocked by: []
---

## Parent

<有 PRD：[需求标题](../PRD.md)；无 PRD 时写一句话需求摘要或指向真实存在的需求来源>

## What to build

<本任务解决的问题，以及完成后用户或系统获得的端到端行为>

## 相关 RULES

- <直接塑造本任务方案的 RULE-NN；没有则写 None。这里只引用短号，不复制规则正文>

## 现状

<理解本方案所需的当前流程、能力缺口和代码事实>

## 方案设计

### <主要实现位置> — <改动目标>

<写清主要处理路径，以及必要的能力复用、数据或状态变化、接口契约、处理顺序和边界>

## 验收

- <操作或请求> → <可观察的预期结果>
- <边界或失败场景> → <可观察的预期结果>
```

## 完成标准

将任务卡交给未参与需求讨论的实现者：如果其无需回看 PRD、询问业务口径或重新选择主要方案，能够从任务卡指明的位置直接开始实施，则任务卡合格。

方案设计应达到以下粒度：

```markdown
### `SupplierAppService.save` — 注册供应商后初始化认证记录

修改现有供应商保存流程，不新增对外接口。

1. 在供应商基本信息落库成功后初始化认证记录。
2. 初始化逻辑复用 `CertificationService.initialize`，不直接操作 Mapper。
3. 只有首次创建供应商时执行，编辑已有供应商时不得重复初始化。
4. 供应商保存与认证初始化使用同一事务；初始化失败时整体回滚。
5. 不改变现有接口的请求和响应结构。
```
