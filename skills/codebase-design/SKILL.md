# Codebase Design

设计**深模块**：用小接口隐藏大量行为，把接口放在清晰接缝处，并通过该接口完成测试。在设计或重构代码时使用这些词汇和原则，目标是为调用者提供杠杆、为维护者提供局部性，并让测试自然发生。

使用已加载的 CONTEXT 术语与 RULE。尚未加载则按项目知识协议执行；知识不可用时继续并如实说明。

## 词汇表

讨论设计时统一使用以下词汇。引用真实代码时保留已有标识和项目术语，不为了统一词汇强行重命名 `Service`、`API`、`Component` 或业务边界。

**模块（Module）**：任何具有接口和实现的结构。它与规模无关，可以是函数、类、包或跨层切片。讨论设计概念时避免用“单元”“组件”或“服务”代替。

**接口（Interface）**：调用者正确使用模块必须知道的全部信息。不只是类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。讨论这一完整表面时避免使用含义更窄的“API”或“签名”。

**实现（Implementation）**：模块内部的代码。它不同于**适配器**：适配器描述接缝处的角色，实现描述其内部内容。讨论接缝时使用“适配器”，其他情况使用“实现”。

**深度（Depth）**：接口提供的杠杆，即调用者或测试每学习一单位接口能够调用多少行为。大量行为隐藏在小接口后面时模块较深；接口几乎与实现同样复杂时模块较浅。

**接缝（Seam）**（Michael Feathers）：无需在调用位置编辑代码就能改变行为的位置，也是模块接口所在的位置。接缝放在哪里与接口包含什么是两个不同的设计决策。它不同于 DDD 中的业务边界。

**适配器（Adapter）**：在接缝处满足接口的具体结构。它描述所填充的角色，而不是内部使用的技术。

**杠杆（Leverage）**：调用者从深度获得的收益。每学习一单位接口能够得到更多能力，一份实现可以服务多个调用点和测试。

**局部性（Locality）**：维护者从深度获得的收益。变更、缺陷、知识和验证集中在一处，而不是散落到调用者中；修复一次，处处生效。

## 深模块与浅模块

**深模块** = 小接口 + 大量实现：

```text
┌─────────────────────┐
│       小接口         │  ← 少量方法、简单参数
├─────────────────────┤
│                     │
│       深实现         │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```text
┌─────────────────────────────────┐
│              大接口              │  ← 方法多、参数复杂
├─────────────────────────────────┤
│              薄实现              │  ← 只是转发
└─────────────────────────────────┘
```

设计接口时询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂度？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部仍可由小型、可 mock、可替换的部分组成，只是这些部分不属于外部接口。模块可以同时拥有实现私有、供自身测试使用的**内部接缝**，以及接口所在的**外部接缝**。
- **删除检验。** 想象删除这个模块：如果复杂度随之消失，它只是转发层；如果复杂度重新散落到多个调用者，它就在发挥价值。
- **接口就是测试面。** 调用者和测试跨越同一个接缝。如果测试想越过接口，模块形状很可能不对。
- **一个适配器是假想接缝，两个适配器才是真实接缝。** 只有确实存在变化时才引入接缝。

## 为可测试性设计

好的接口让测试自然发生：

1. **接收依赖，不要在内部创建依赖。**

   ```typescript
   // 易于测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要只产生副作用。**

   ```typescript
   // 易于测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **保持较小的表面积。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**只有一个**接口**，供调用者和测试使用。
- **深度**是**模块**相对于其**接口**的属性。
- **接缝**是**模块接口**所在的位置。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用者产生**杠杆**，为维护者产生**局部性**。

## 不采用的表述

- **用实现行数与接口行数之比衡量深度**（Ousterhout）：这会奖励填充实现。这里用接口杠杆衡量深度。
- **把“接口”理解为 TypeScript `interface` 关键字或类的 public 方法**：范围太窄，这里的接口包含调用者必须知道的全部事实。
- **使用“边界”表示接缝**：它容易与 DDD 的限界上下文混淆，应使用“接缝”或“接口”。
