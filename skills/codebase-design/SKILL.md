# Codebase Design

把本 Skill 当作共享参考层，不当作独立流程运行。它不自行扫描代码库、不发起重构、不推进决策会话，也不产生固定产物；由 `to-task`、`grill-with-docs`、`impl`、`code-review` 或当前用户任务决定范围、步骤、副作用和停止条件。

先按 `docs/agents/domain.md` 定位并使用相关 `CONTEXT.md`，并遵守全部项目 RULES。领域词汇负责命名业务概念，本 Skill 的词汇负责描述模块形状；真实代码标识、项目术语和已记录规则优先，不得为了统一词汇强行重命名已有 `Service`、`API`、`Component` 或业务边界。

## 共享词汇

- **模块（Module）**：具有接口与实现的结构，可以是函数、类、包或跨层切片，不等同于目录。
- **接口（Interface）**：调用者正确使用模块必须知道的全部信息，包括入口、参数、不变量、调用顺序、错误模式、配置要求和性能特征，不只指类型签名或语言关键字。
- **实现（Implementation）**：模块在接口背后完成行为的内部代码。
- **深度（Depth）**：接口提供的杠杆；调用者每学习一单位接口能获得多少行为。大量行为藏在小接口后面时模块较深，接口几乎与实现同样复杂时模块较浅。
- **接缝（Seam）**：无需在调用点修改代码即可替换行为的位置，也是模块接口所在的位置。它与领域 Context 的业务边界不是同一个概念。
- **适配器（Adapter）**：在接缝处满足接口的具体实现，描述其角色而非内部技术。
- **杠杆（Leverage）**：调用者从模块深度获得的收益；一次实现服务多个调用点与测试。
- **局部性（Locality）**：变更、缺陷、知识与验证集中在一处，而不是泄漏到多个调用者。

讨论模块形状时优先使用这些词汇，但不得覆盖目标项目已经定义的领域术语或真实代码名称。

## 判断准则

1. **从接口判断深度。** 不按文件数或实现行数判断深浅；检查调用者需要学习和重复处理多少细节。
2. **执行删除测试。** 想象删除候选模块：复杂度消失，说明它可能只是转发；复杂度重新散落到多个调用者，说明它正在集中有价值的行为。
3. **把接口作为主要测试面。** 优先通过调用者使用的同一接口验证可观察行为。测试必须越过接口读取内部状态时，重新检查模块形状或测试位置。
4. **只为真实变化建立接缝。** 至少能指出两个有意义的 adapter 或行为变体时再引入接缝；不得只为形式、假想扩展或方便 mock 增加间接层。
5. **追求局部性与杠杆。** 将跨调用者重复的规则、顺序和错误处理吸收到模块内部，同时避免形成承载无关职责的巨型入口。

## 设计接口

检查候选接口：

- 能否减少入口数量、参数和调用顺序要求；
- 能否把不变量、错误处理、配置和协作顺序隐藏到实现内部；
- 调用者是否仍需拼装内部步骤、理解内部状态或在多处重复规则；
- 接口是否覆盖真实用例，而不是为未知未来预留宽泛扩展点；
- 测试是否能通过接口观察结果，并在内部重构后继续成立；
- 依赖应由模块内部直接使用、放在内部接缝，还是作为外部接缝注入。

深化一组浅模块、决定依赖接缝或迁移测试时，读取 [DEEPENING.md](./DEEPENING.md)。仅当用户明确要求比较多种接口方案，或流程型 Skill 已确认这是影响显著且难以逆转的接口决策时，读取 [DESIGN-IT-TWICE.md](./DESIGN-IT-TWICE.md)。

## 输出边界

只向当前流程提供词汇、判断和设计结果。是否提问、写任务卡、修改代码、删除测试、提交或记录项目规则，完全由调用它的流程型 Skill 与当前用户授权决定。不得因为加载本 Skill 扩大任务范围或重新打开已经收口的主要方案。
