# 深化模块

在已知依赖的情况下，安全地深化一组浅模块。本文使用 [SKILL.md](./SKILL.md) 中的**模块**、**接口**、**接缝**和**适配器**词汇。

## 依赖分类

评估深化候选时，先对依赖分类。依赖类别决定深化后的模块如何跨接缝测试。

### 1. 进程内依赖

纯计算、内存状态，没有 I/O。始终可以深化：合并模块，并直接通过新接口测试，不需要适配器。

### 2. 本地可替代依赖

具有本地测试替代物的依赖，例如用 PGLite 替代 Postgres、用内存文件系统替代真实文件系统。存在可信替代物时可以深化，在测试套件中运行替代物并测试深化后的模块。接缝保留在内部，不在模块外部接口上暴露 port。

### 3. 自有远程依赖（Ports & Adapters）

跨网络调用的自有服务，例如微服务或内部 API。在接缝处定义 **port**（接口），深模块持有业务逻辑，传输方式作为**适配器**注入。测试使用内存适配器，生产使用 HTTP、gRPC 或消息队列适配器。

建议形式：*“在接缝处定义 port，生产环境使用 HTTP 适配器，测试使用内存适配器。这样即使模块跨网络部署，逻辑仍集中在一个深模块中。”*

### 4. 真实外部依赖（Mock）

无法控制的第三方服务，例如 Stripe 或 Twilio。深化后的模块通过注入 port 接收外部依赖，测试提供 mock 适配器。

## 接缝纪律

- **一个适配器是假想接缝，两个适配器才是真实接缝。** 至少有两个合理适配器时才引入 port，通常是生产适配器与测试适配器。只有一个适配器的接缝只是间接层。
- **区分内部接缝与外部接缝。** 深模块可以拥有实现私有、供自身测试使用的内部接缝，也可以拥有接口所在的外部接缝。不要仅因为测试使用内部接缝就把它暴露到外部接口。

## 测试策略：替换，不叠加

- 深化后的接口测试就位后，浅模块的旧单元测试会变成负担，应当删除。
- 在深化后的模块接口上编写新测试，**接口就是测试面**。
- 测试通过接口断言可观察结果，不断言内部状态。
- 测试描述行为而非实现，因此应能在内部重构后继续成立。如果实现变化就必须改测试，说明测试越过了接口。
