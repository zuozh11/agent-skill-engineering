# Design It Twice

仅当用户明确要求比较多种接口方案，或流程型 Skill 已确认当前接口决策影响显著且难以逆转时使用。不得把本方法当作 `codebase-design` 的默认流程。

## 1. 固定问题空间

先从代码、项目文档和当前需求中查证并写清：

- 新接口必须满足的行为、约束和项目 RULES；
- 当前调用者、依赖、错误模式和必须保留的兼容性；
- 各依赖在 [DEEPENING.md](./DEEPENING.md) 中的分类；
- 接口需要隐藏的复杂度，以及不得扩大的任务范围。

事实不足时由当前流程型 Skill 负责查证或提问，本方法不得自行推进未确认决策。

## 2. 生成不同方案

宿主支持子 Agent 且当前任务允许并行设计时，让至少三个相互独立的子 Agent 分别采用不同约束：

1. 最小化接口，优先提高每个入口的杠杆；
2. 优先覆盖已确认的扩展需求，不为未知未来设计；
3. 优化最常见调用者，使默认路径最简单；
4. 仅在存在真实跨接缝依赖时，额外设计 ports-and-adapters 方案。

宿主不支持子 Agent 时，在相互隔离的三个分析轮次中顺序生成方案，完成全部方案前不得用上一方案的结论收窄下一方案。

每个方案必须包含：

- 接口入口、参数、不变量、调用顺序与错误模式；
- 典型调用示例；
- 接口背后隐藏的实现复杂度；
- 依赖与 adapter 策略；
- 在深度、局部性、杠杆和迁移成本上的取舍。

## 3. 比较并交还当前流程

按深度、局部性、接缝位置、调用者成本、测试面和迁移风险比较方案，给出明确推荐；只有组合后仍保持职责一致时才提出混合方案。

把推荐与未决问题交还调用本方法的流程型 Skill。是否要求用户确认、写入任务卡或进入实现，由该流程决定。
