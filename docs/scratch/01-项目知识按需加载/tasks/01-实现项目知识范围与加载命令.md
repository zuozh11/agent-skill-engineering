## Parent

[项目知识按需加载 PRD](../PRD.md)

## What to build

把现有 `read-rules.py` 的全量 RULE 读取能力升级为项目内单文件 `project-knowledge.mjs`：Agent 能先查看可选的 Context 与 RULE 场景，再一次取得本次任务所需的完整项目知识；知识作者也能用同一套解析逻辑检查实际依赖的格式。

本任务只建立 CLI 和 V2 文档契约，不安装 Hook、不修改真实 Agent 配置，也暂不删除旧入口。

## 现状

- `skills/setup-agent-skills/scripts/read-rules.py` 只会按文件名合并全部 RULE，不能选择 Context、RULE 场景或展开 `references`。
- `skills/setup-agent-skills/domain.md`、`context-format.md`、`rules-format.md` 仍描述旧的全量读取与 `RULE-NN` 命名。
- 仓库没有 Node 测试基础设施；新脚本必须只依赖 Node 标准库，并通过其公开子命令验证行为。

## 方案设计

### `skills/setup-agent-skills/scripts/project-knowledge.mjs` — 提供一个深的项目知识入口

新增单文件脚本，对外只暴露 `validate-context`、`validate-rules`、`scope`、`load` 四个子命令；布局发现、受控 Frontmatter、Context Map、RULE 文件名、场景和引用图解析都留在脚本内部，并由四个入口复用，调用者不需要拼装内部步骤。

1. 脚本以自身所在的 `docs/agents/` 为锚点定位领域文档根，不依赖调用时工作目录；目标项目没有采用单/多 Context 布局时静默成功。
2. `scope` 输出紧凑 JSON：单 Context 只列 RULE 场景；多 Context 按 Map 顺序列 Context 路径与说明，并列出 RULE 场景和场景内文件。
3. `load` 接收可重复的 `--context`、`--rule`，固定加入根级 Context 文档，展开所选场景及递归 `references`，去重后一次输出带相对路径分隔的完整正文。“必读”只是普通场景，不自动加入。
4. 完成收集后再写 stdout；无效选择或知识损坏时给出可读错误，不输出半截正文。循环引用用访问集合终止并提醒，不作为失败。
5. validator 只检查这套实现真正依赖的布局、元数据、文件名、Map 链接和引用，不扩展成通用 Markdown/YAML 校验器，也不自动修复文件。
6. 使用 Node 内置测试能力覆盖单/多 Context、无 RULE、场景选择、递归引用、循环、去重、错误不产生部分输出，以及从不同工作目录调用同一脚本。

### V2 种子文档 — 与 CLI 使用同一份格式契约

重写 `skills/setup-agent-skills/domain.md`、`context-format.md`、`rules-format.md`：

- `domain.md` 只保留知识维护判断、落点和冲突处理，不再要求任务开始时全量读取 RULE；
- `context-format.md` 说明单/多 Context、`description` 和 Map 注册方式；
- `rules-format.md` 说明场景文件名、`references` 和生命周期；
- 文档只写作者需要知道的规则，机器细节以 CLI 的实际行为为准，避免复制第二套解析规范。

## 验收

- 在单 Context fixture 执行 `scope`，再选择一个 RULE 场景执行一次 `load` → 输出包含 `docs/CONTEXT.md`、该场景和递归引用的完整正文，不自动加入其他场景。
- 在多 Context fixture 选择两个 Context 和两个 RULE 场景执行一次 `load` → Map、所选 Context、所选及被引用 RULE 各出现一次，顺序稳定。
- 构造循环引用 → `load` 正常结束且每个文件只出现一次，validator 给出可读提醒。
- 构造坏 Map、坏 Frontmatter、悬空引用和未知选择 → 命令非零退出、stderr 能定位文件，stdout 为空。
- 使用约 8 个 Context、40 个 RULE 的 fixture 执行最大选择 → 末尾文件和结束正文完整存在，证明 CLI 自身没有截断。
